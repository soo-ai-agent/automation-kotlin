# 추상화와 이름 짓기

읽기 좋은 코드를 만드는 단 하나의 기준은 **추상화**다. 클린 코드의 개별 조언들은 전부 이것의 다른 얼굴이다.

읽힌다 → 이해된다 → 고치기 쉽다 → 시간과 자원이 덜 든다. 이 사슬이 규칙을 지키는 이유 전부다.

## 추상화란 무엇인가

프로그램은 **데이터 + 코드**다. 추상화는 그중 **중요한 것만 남기고 나머지를 버리는 일**이다.

- 구체 → 추상: 정보를 덜어낸다 (추상화)
- 추상 → 구체: 남은 것으로 나머지를 유추한다 (이해)

덜어내고 남긴 것에 이름을 붙이면 **층**이 생긴다. 그 층이 추상화 레벨이다.

컴퓨터가 0과 1만으로 고도의 일을 하는 것도 같은 원리다 — 비트를 묶어 자료형, 연산을 묶어 함수,
함수를 묶어 서비스. **묶고 이름 붙이기를 겹겹이 쌓은 결과**가 지금 우리가 쓰는 언어다.

### 잘못된 추상화

추상만 보고 구체를 유추하지 못한다면 넷 중 하나다.

1. 중요한 정보를 부각시키지 못했다
2. 덜 중요한 것을 남기고 중요한 것을 버렸다
3. 읽는 사람과 공유하는 문맥이 없다
4. **무엇이 중요한지의 기준이 도메인마다 다르다**

4번이 핵심이다. `sync` 가 외부 시스템 동기화인지 DB 동기화인지는 도메인이 정한다.
**적절한 추상화란 그 도메인의 문맥 안에서 핵심만 남기는 것**이지, 보편적으로 옳은 추상화는 없다.

잘못된 추상화의 대가는 크다. 읽는 사람이 코드를 열어봐야만 뜻을 알 수 있게 되고,
그 순간 이름은 정보가 아니라 소음이 된다.

## 이름 짓기

**이름을 짓는 것이 가장 흔하고 가장 중요한 추상화 행위다.**

좋은 이름의 조건은 둘이다 — ① 구체에서 핵심만 뽑아 드러낼 것 ② 우리 도메인 안에서 통할 것.

### 단수와 복수를 구분한다

`-s` 하나로 "이게 하나인가 여럿인가"를 공짜로 전달한다.

```kotlin
val order: Order            // 하나
val orders: List<Order>     // 여럿
```

파일명·클래스명·테이블명의 단복수 규약은 계층 스킬이 정한다 — **kotlin-entity**·**kotlin-dto**·**kotlin-module-layout**.

### 줄이지 않는다

줄임말은 **가독성을 팔아 타이핑 몇 글자를 사는 거래**다. 대부분 손해다.

관용어가 된 것만 허용한다: `id`, `url`, `db`, `lat`, `lon`.
**`cnt` 는 허용하지 않는다** — `count` 와 두 글자 차이다.

```kotlin
// 피할 형태
val diffCnt: Int
val res = orderClient.getOrder(orderId)

// 표준형
val diffCount: Int
val order = orderClient.getOrder(orderId)
```

줄임말이 통하는 것은 짧아서가 아니라 **문맥이 있어서**다. 문맥이 없으면 통하지 않는다.

> `res`·`msg`·`obj`·`e` 같은 이름이 이미 있는 자리는 **보이는 족족 고치지 않는다** — 요청 범위 밖이다 (5대 원칙 제 2).
> 새로 쓰지 말고, 그 줄을 고칠 일이 생기면 같이 고친다. 예외는 `catch (e: XxxException)` 의 `e` 다 — 관용이다.

### 은어를 쓰지 않는다

판정 한 문장: **"오늘 합류한 사람이 이 이름을 단번에 이해하는가?"**

농담에서 나온 말, 지금 팀만 아는 말은 쓰지 않는다. 도메인 용어를 쓰고,
도메인 용어가 아직 정해지지 않았다면 **이름 짓기보다 용어 정하기가 먼저다.**

기준은 셋이다 — 중학교 영어 수준인가, 한국어 한 단어로 옮겨지는가, 이미 쓰는 낱말과 겹치지 않는가.

### 설명을 붙여야 하는 이름은 이름이 나쁜 것이다

함수나 클래스에 "이것이 무엇을 하는지" 설명을 달고 싶어지면, **설명을 쓰지 말고 이름을 고친다.**
설명이 필요하다는 것은 이름이 제 일을 못 하고 있다는 신호다.

```kotlin
// 피할 형태 — 이름이 못 한 말을 KDoc 이 대신한다
/** 판정의 재료를 읽는다. 모든 요청이 같은 것을 보므로 캐시가 대신 답할 수 있다. */
private fun loadSavings(requestId: String): AllSavings

// 표준형 — 캐시에서 읽는다는 사실을 호출 한 줄이 그대로 말한다
val savings: AllSavings = allSavingsCache.get(requestId)
```

**함수·클래스에 기능 설명을 쓰지 않는다.** 남기는 것은 코드가 말할 수 없는 것뿐이다 —
규칙을 어긴 이유(`?`·`Any`·`Map` 을 쓴 사정), 외부 제약, 의도된 예외.

공개 API 문서로 쓰이는 자리(컨트롤러 엔드포인트의 OpenAPI 설명, 응답 DTO)는 예외다. 그건 설명이 아니라 산출물이다 (**kotlin-api-docs**).

판정: **그 설명을 지웠을 때 잃는 정보가 있는가.** 없으면 그 설명은 없어야 한다(**kotlin-common** 주석 규칙).

### 같은 것을 두 이름으로 부르지 않는다

한 개념에 낱말 하나를 고정한다. `member` 와 `user`, `order` 와 `purchase` 가 섞여 있으면
읽는 사람이 "이 둘이 같은 것인가"를 매번 추측한다.

**외부에서 들어온 낱말은 경계에서 우리 낱말로 바꾼다.** 외부 API 가 `SavingProduct` 라 부르더라도
안쪽은 `Product` 하나로 간다 — 바꾸는 자리는 `clients/client-*` 한 곳이다(제 4원칙 · 데이터 흐름).

낱말이 세 개를 넘으면 머리로 기억하지 말고 **저장소에 어휘 사전을 둔다.**
새 이름을 짓기 전에 사전을 보고, 사전에 없는 낱말이 필요하면 사전에 먼저 적는다.
규칙 문서가 쓰는 낱말은 `.claude/skills/core-principles/references/glossary.md` 가 고정한다.

### Boolean 을 돌려주면 `is`·`has`·`can` 으로 시작한다

`check` 로 시작하는 이름은 "검사하고 끝"(`Unit`)으로 읽힌다. 값을 돌려준다면 이름이 그 값을 말해야 한다.

```kotlin
// 피할 형태 — 이름만 보면 반환값이 있는지 모른다
fun checkToken(tokenId: String): Boolean

// 표준형
fun isValidToken(tokenId: String): Boolean
```

같은 이유로 `get` 은 값을 돌려주는 자리에만 쓴다.

**`get`·`find` 규약은 이 저장소에서 뜻이 다르다** — `getXxx` 는 없으면 예외를 던지고, `findXxx` 는 없으면 `null` 을 낸다 (**kotlin-implement**).
이름을 고를 때 둘을 바꿔 쓰지 않는다.

## 함수 하나 = 주제 하나

**한 문단의 주제가 하나이듯, 한 함수의 주제도 하나다.**

함수 이름이 본문을 추상화한다. 두 가지 일을 하고 있으면 이름으로 본문을 유추할 수 없다.

판정: **이름을 짓기 어렵다면 십중팔구 두 가지 일을 하고 있다.** 이름을 고민하지 말고 쪼갠다.

쪼갤 때는 **지역적으로 자르지 말고 전체 맥락을 담는 주제**로 자른다.
`processStep2` 는 자른 위치의 이름이고, `refreshFromPaymentGateway` 는 주제의 이름이다.

### 선언부 전체가 추상화에 기여한다

```kotlin
fun getList(query: OrderListQuery, actor: Actor): OrderListResult
```

| 자리 | 무엇을 말하나 |
|---|---|
| 이름 | 이 함수의 주제 |
| 파라미터 | **이 일을 하려면 무엇이 필요한지**를 바깥에 드러내는 창 |
| 반환 타입 | 무엇을 돌려받는지. `Unit` 대신 돌려줄 값이 정말 없는지 먼저 본다 |

세 자리가 함께 읽혀야 본문을 안 열고도 뜻이 통한다. **길이가 아니라 의미가 기준이다** — 세 줄짜리도 주제가 하나면 그것으로 족하다.

함수를 뽑아낼 때 스스로에게 묻는다.

- 이름이 하는 일을 정확히 말하는가
- 두 가지 일을 하고 있지 않은가
- 더 포괄적인 이름이 있는가
- 파라미터가 적절한가 — 필요 없는 것을 받고 있지 않은가
- 반환 타입이 적절한가

### 한 번만 쓰이는 함수는 뽑기 전에 한 번 더 본다

**판정은 하나 — 호출부에 그대로 넣었을 때 더 잘 읽히는가.** 이름이 본문보다 덜 말하면 합친다.

이름이 공식·관용구를 담으면 남긴다. 지우는 대신 **그 데이터를 가진 타입의 메서드나 확장 함수로 옮기는** 편이 나을 때도 많다(**object-design**).

## 추상화 레벨을 맞춘다

**함수 안(내부 세계)은 낮은 레벨, 함수 밖(호출부)은 높은 레벨이다.
그리고 한 세계 안에서는 레벨이 같아야 한다.**

높은 레벨의 호출이 이어지다가 갑자기 낮은 레벨의 코드가 튀어나오면 읽는 사람이 걸려 넘어진다.

```kotlin
// 피할 형태 — 한 함수 안에 세 레벨이 섞여 있다
@Transactional
fun list(query: OrderListQuery, actor: Actor): OrderListResult {
    adminSessionService.requireValidSession(actor)                       // 높다

    val page = orderRepository.findPage(query.page, query.size)
    val memberIds = page.content.mapNotNull { it.memberId }.toSet()      // 낮다
    val memberMap = memberRepository.findAllById(memberIds).associateBy { it.id }

    val items = page.content.map { entity ->
        OrderItem(
            id = entity.id,
            memberEmail = memberMap[entity.memberId]?.email ?: "",       // 더 낮다
        )
    }
    return OrderListResult(items, page.totalElements)
}
```

```kotlin
// 표준형 — 한 레벨로 통일한다. 낮은 것은 이름을 붙여 아래로 내린다
@Transactional(readOnly = true)
fun getList(query: OrderListQuery, actor: Actor): OrderListResult {
    adminSessionService.requireValidSession(actor)

    val orders: Page<Order> = orderFinder.findPage(query)
    return orderListAssembler.assemble(orders)
}
```

위에서 아래로 한 번에 읽힌다. 세부가 궁금하면 그때 `orderListAssembler` 를 연다.

### 파일 하나도 한 레벨이다

**함수 안의 문장들이 같은 높이여야 하듯, 파일 안의 함수들도 같은 높이여야 한다.**

이 저장소는 **파일 하나에 최상위 선언 하나**다(`rules/code-review.md` MUST). 그래서 이 규칙은 대개 "이 클래스가 한 층에 있는가"로 나타난다.

판정: **파일 이름을 듣고 떠올린 것과 다른 층의 메서드가 그 안에 있는가.**
`OrderService.kt` 를 열었는데 날짜 포맷 함수가 있으면 어긋난 것이다.

낮은 층이 한두 함수뿐이라 파일을 새로 만들기 아깝다면, **파일을 만들지 말고 그 일을 이미 가진 타입에게 넘긴다** —
값을 아는 쪽이 그 값으로 하는 일도 갖는다(**object-design**). 확장 함수가 그 자리다.

새 파일도 새 타입도 답이 아닐 만큼 사소하면, 그 함수는 애초에 필요 없을 가능성이 높다(**ponytail**).

**예외는 파일이 스스로 밝힌 경계다.** 외부 응답을 받는 `clients/client-*` 는 파일 전체가
가장 낮은 레벨이므로 안에서 원본 응답 타입을 다뤄도 어긋난 것이 아니다 — 단 **그 타입이 모듈 밖으로 나가지 않아야 한다.**

### 모듈 구조가 곧 추상화 레벨이다

| 계층 | 레벨 | 여기에 있어야 할 것 |
|---|---|---|
| 컨트롤러 | 가장 높다 | 요청 받기, 도메인 서비스 호출, 응답 조립 |
| 도메인 서비스 | 높다 | 흐름 조립, 트랜잭션 경계 |
| 구현 레이어 (Finder·Appender) | 중간 | 재사용 단위, 엔티티↔도메인 모델 변환 |
| 엔티티·도메인 모델 | 중간 | 도메인 판단과 상태 전이 |
| 리포지토리 | 낮다 | 쿼리 |
| clients | 가장 낮다 | 외부 호출, 원본 응답 |

**컨트롤러가 `Map` 을 뒤지고 있다면 레벨이 어긋난 것이다.**

```kotlin
// 피할 형태 — 컨트롤러가 응답 내부를 헤집고 예외까지 삼킨다
@GetMapping("/api/v1/orders")
fun getList(actor: Actor): ResponseEntity<Map<String, Any>> {
    val orders = orderService.list(actor)
    val rows = orders.map { order ->
        val row = order.toMutableMap()
        try {
            row["addresses"] = extractNonFloatingAddresses(order)
        } catch (e: Exception) {
        }
        row
    }
    return ResponseEntity.ok(mapOf("data" to rows))
}
```

`Map` 조립, 제자리 수정, 예외 삼키기 — 전부 아래 레벨의 일이거나 아예 하면 안 되는 일이다.

계층별 상세 규칙은 **kotlin-controller**·**kotlin-domain-service**·**kotlin-implement**·**kotlin-repository** 에 있다.

**엔티티는 구현 레이어 위로 올라가지 않는다** — 이것도 같은 규칙의 한 얼굴이다. 낮은 층의 타입이 높은 층 시그니처에 나타나면 레벨이 새어 나온 것이다.

## 읽는 사람의 머리를 아껴 쓴다

읽는 사람이 동시에 기억해야 할 것이 적을수록 좋은 코드다.

### 사고의 깊이를 줄인다

중첩된 분기·반복은 읽는 사람에게 여러 조건을 동시에 붙들게 한다. 함수로 뽑아 층을 나눈다.

```kotlin
// 피할 형태
for (order in orders) {
    for (item in order.items) {
        if (item.status == ItemStatus.SHIPPED && item.quantity > 0) {
            collect(item)
        }
    }
}

// 표준형
for (order in orders) {
    collectShippedItems(order)
}
```

판단 축이 둘 이상이면 중첩 `if` 가 아니라 lookup 이나 타입으로 옮긴다(`rules/code-review.md` 「분기를 쌓지 않는다」).

### 체인을 쌓아 층을 숨기지 않는다

Kotlin 은 `?.let {}.map {}.filter {}` 로 여러 층을 한 줄에 눌러 담기 쉽다. 그러면 중간 이름이 사라진다.

**줄 수가 줄어든 만큼 읽는 사람이 머리로 복원해야 한다.** 판단·반복은 람다로 압축하지 않고 `if`/`for` 로 풀어서 쓴다(**kotlin-common**).

### 쓰는 자리 가까이에서 선언한다

변수를 20줄 위에서 만들어 두면, 쓰는 자리에서 위로 거슬러 올라가야 한다. **쓰기 직전에 만든다.**

### 빈 줄도 정보다

빈 줄은 "여기까지가 한 덩어리"라는 신호다. 의미 단위로 끊어 준다.
반대로 아무 데나 넣은 빈 줄은 없는 것보다 나쁘다 — 없는 경계를 있다고 말하기 때문이다.

### 나열 순서로도 말한다

- **변수** — 쓰는 순서대로.

- **함수** — 공개 메서드를 위에. 객체가 바깥에 무엇을 제공하는지가 먼저 보여야 한다.
  공개 메서드끼리는 **상태 변경 → 판별 → 조회** 순으로 묶는다. 비슷한 것을 또 만드는 실수를 막는다.

- **비공개 메서드** — 공개 메서드에서 불린 순서대로 그 아래에. 공용이면 가장 아래.

이 저장소의 "위에서 아래로" 규칙(**kotlin-common** 코드 스타일)이 같은 말이다.

### 패키지 경로가 문맥을 준다

`order.domain.model` 안의 `Status` 는 `OrderStatus` 일 필요가 없다. **경로가 이미 문맥을 주고 있기 때문**이다.

다만 `core:core-enum` 처럼 **여러 모듈이 공유하는 자리**에서는 문맥이 없으므로 도메인 이름을 붙인다.

너무 안 쪼개도, 너무 잘게 쪼개도 관리가 어려워진다. 큰 폭의 패키지 변경은 팀 합의 후에 한다 — 남의 작업과 충돌한다.

## 이미 다른 스킬이 정한 것

여기에 본문을 다시 쓰지 않는다. 전부 같은 추상화 이야기의 다른 얼굴이다.

| 주제 | 정본 |
|---|---|
| guard clause·early return, 부정어, 매직 넘버, 반복문 불변식 | **kotlin-common** |
| `when` 소진 검사, sealed 상태 표현, `!!` 금지 | **kotlin-style** |
| `get`/`find` 규약, 구현 레이어 분리 | **kotlin-implement** |
| 주석은 "왜"만, 이름으로 풀 수 있으면 이름으로 | **core-principles** 제 1원칙 「주석을 달기 전에 코드를 먼저 푼다」 |
| 같은 개념에 낱말 하나 | **core-principles** 제 1원칙 「한 개념은 한 낱말로 부른다」 |
| 값을 꺼내 밖에서 바꾸지 않기, 세터 대신 도메인 메서드 | **core-principles** 제 5원칙 |
| 파생값을 저장하지 않기, 단일 원본 | **core-principles** 제 4원칙 |
| 책임 배치, 응집도·결합도, 다형성, 상속보다 합성 | **object-design** (상세는 `reference.md`) |
| 모듈 경계와 의존 방향 | **kotlin-module-layout** |
| 구현체 하나뿐인 인터페이스, 이른 추상화 | **ponytail** |

## 오버엔지니어링 — 추상화도 과하면 해롭다

**정보를 숨기는 것이 추상화다. 필요 없는 곳에서 숨기면 그냥 안 보이는 것이다.**

구현체가 하나뿐인 인터페이스, 아직 안 쓰는 확장 지점, 이른 계층 분리는 읽는 사람에게
"왜 이렇게 했지"라는 질문만 남긴다. 상세 판정은 **ponytail** 이 한다.

이 저장소에서는 **구현이 하나뿐인데 확장 지점을 통째로 신설한 것이 차단 사유**다 — 참고 코멘트가 아니라 머지가 막힌다.

그리고 **클린 코드도 만능이 아니다.** 지금 급히 나가야 하는 배포 앞에서 스타일 지적을 붙드는 것은
우선순위를 못 읽은 것이다. 기술 부채를 지기로 했다면 `ponytail:` 주석으로 한계와 업그레이드 경로를 남긴다.

## 적발 신호

| 신호 | 무엇이 어긋났나 | 심각도 |
|---|---|---|
| 함수 이름을 짓기 어렵다 | 두 가지 일을 하고 있다 | Important |
| 이름에 `and`·`or` 가 들어간다 | 〃 | Important |
| 높은 레벨 호출 사이에 `Map` 조작·필드 파헤치기가 섞여 있다 | 추상화 레벨 불일치 | Important |
| 컨트롤러가 `Map` 을 조립하거나 응답 내부를 헤집는다 | 계층 레벨 이탈 | Critical |
| 엔티티가 서비스·컨트롤러 시그니처에 나타난다 | 낮은 층 타입이 위로 샜다 (`rules/code-review.md` MUST) | Critical |
| 클래스 이름이 말하는 층과 다른 층의 메서드가 섞여 있다 | 파일 레벨 불일치 | Important |
| 함수·클래스에 "무엇을 하는지" KDoc 이 붙어 있다 | 이름이 제 일을 못 한다 | Important |
| 같은 개념을 두 낱말로 부른다 (`member`/`user`) | 어휘가 고정되지 않았다 | Important |
| `checkXxx(): Boolean` | 이름이 반환값을 말하지 않는다 | Important |
| `findXxx` 가 예외를 던지거나 `getXxx` 가 `null` 을 낸다 | 규약을 어겨 호출부가 이름을 못 믿는다 | Important |
| `cnt`·`res`·`msg` 를 새로 만든다 | 줄임말 | Code Smell |
| 단수 이름이 목록을 담는다 (`val order: List<Order>`) | 단복수 불일치 | Code Smell |
| 변수를 만든 자리와 쓰는 자리가 20줄 넘게 떨어져 있다 | 읽는 사람의 부담 | Code Smell |
| 중첩 `for`·`if` 가 3단 이상이다 | 사고의 깊이 | Important |
| 체인 한 줄이 세 층을 삼켰다 | 중간 이름이 사라졌다 | Important |
| 이름을 못 알아들어 정의를 열어봐야 한다 | 은어이거나 도메인 용어가 아니다 | Important |

## 심각도

- **Critical** — 계층 붕괴, 변경이 번지는 구조 → 머지 전 수정

- **Important** — 유지보수성, 과설계 → 수정 권장

- **Code Smell** — 참고 코멘트

## 체크리스트

- [ ] 이 함수의 주제를 한 문장으로 말할 수 있는가
- [ ] 이름·파라미터·반환 타입만 보고 본문을 유추할 수 있는가
- [ ] 함수 안의 문장들이 같은 높이에 있는가
- [ ] 클래스 안의 메서드들이 같은 높이에 있는가 (클래스 이름이 그 층을 말하는가)
- [ ] 낮은 층 타입(엔티티·외부 응답)이 위 계층 시그니처에 나타나지 않는가
- [ ] 설명을 붙이고 싶어진 이름이 없는가 (있다면 이름을 고쳤는가)
- [ ] 같은 개념에 낱말 하나만 쓰고 있는가
- [ ] Boolean 을 돌려주는 함수가 `is`·`has`·`can` 으로 시작하는가
- [ ] `get`/`find` 규약을 지켰는가
- [ ] 단수·복수가 실제 개수와 맞는가
- [ ] 새로 만든 줄임말이 없는가
- [ ] 체인으로 중간 이름을 지우지 않았는가
- [ ] 오늘 합류한 사람이 이 이름들을 이해하겠는가
- [ ] 공개 메서드가 위에, 비공개가 아래에 있는가
- [ ] 지금 필요 없는 층을 만들지 않았는가
