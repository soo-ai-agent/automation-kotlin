# 3대 원칙

저장소 전체에 적용되는 최상위 원칙이다. 영역도 언어도 가리지 않는다 — 백엔드·프론트엔드·CI 스크립트 어디서든 같다.

다른 규칙 문서(`kotlin-*`, `frontend-*`, `ponytail`, `oop-responsibility-design`, `rules/code-review.md`)는 모두 이 원칙에 종속된다.

충돌하면 이 문서가 앞선다.

1. **단순함이 최우선** — 읽는 사람이 먼저다

2. **최소 수정, 무파괴** — 지금도, 나중에도 적게 고친다

3. **데이터의 흐름과 통제** — 하나의 출처, 변하지 않는 형태, 드러나는 변경 지점

셋이 향하는 곳은 같다. 사람이 나중에 열어봐도 바로 이해하고 개입할 수 있는 코드를 남긴다.

---

## 제1원칙 — 단순함이 최우선

누구든지 처음 봐도 위에서 아래로 읽어 내려가며 이해되는 코드를 쓴다. 영리함보다 명료함, 압축보다 풀어쓰기.

아래 두 원칙과 저장소의 모든 규칙이 이 원칙에 종속된다 — 어떤 규칙을 지키려다 코드가 읽기 어려워졌다면 방향이 틀렸다.

지금 필요 없는 것을 만들지 않는 규칙(YAGNI, 사다리, 요청받지 않은 추상화·설정화 금지)은 **ponytail** 이 상세를 담당한다.

---

## 제2원칙 — 최소 수정, 무파괴

기능을 추가할 때는 기존 코드를 최소한으로만 건드리고, 이미 동작하는 것을 절대 깨지 않는다. 이 프로젝트에 이미 있는 패턴을 찾아 그대로 따르고, 새 방식·새 구조를 발명하지 않는다.

지금 최소로 고치는 것에서 끝나지 않는다. 나중에 요구가 바뀌어도 최소로 고칠 수 있게 남긴다 — 고칠 지점이 적고, 그 지점을 구조와 컴파일러가 짚어줘야 한다.

요구는 바뀐다. 필드가 늘고, 이름이 바뀌고, 새 종류가 생긴다. 그때 **고쳐야 할 곳이 몇 군데인지**, 그리고 **그곳을 사람이 찾아 헤매야 하는지**가 유지보수성이다.

리뷰에서 말하는 "유지보수성"이 이 원칙의 다른 이름이다.

### 이 원칙의 목표는 유지보수성을 높이는 것이다

"적게 고친다"는 수단이고, **목표는 다음 변경이 쉬워지는 것**이다. 둘을 바꿔 놓으면 규칙을 지키면서 코드는 나빠진다 —
지금 diff 를 줄이려고 판단을 호출부에 복사하면 이번 변경은 작아지지만 다음 변경은 두 곳이 된다.

그래서 판정은 diff 크기가 아니라 아래 다섯 질문으로 한다. 이어지는 다섯 갈래가 각각 그 답이다.

| 물어볼 것 | 좋은 상태 | 이 문서의 어느 갈래 |
|---|---|---|
| 이 규칙이 바뀌면 몇 군데를 고치나 | 한 곳 | 고칠 지점을 하나로 모은다 |
| 고칠 곳을 무엇이 알려주나 | 컴파일러 | 컴파일러가 고칠 곳을 짚게 한다 |
| 빠뜨린 분기가 언제 드러나나 | 컴파일할 때 | 닫힌 값 집합은 소진 검사로 잠근다 |
| 새 종류가 생기면 무엇을 하나 | 추가만 | 새 종류 추가가 '추가'로 끝나게 한다 |
| 고칠 파일을 어떻게 찾나 | 이름으로 | 이름이 도메인을 닮게 한다 |

**측정은 "요구사항 하나를 더 넣어 보고 고치는 곳을 세는 것"이다.** 새 종류 추가가 클래스(또는 파일) 추가만으로 끝나면 좋은 설계이고,
기존 코드를 여러 군데 열어야 하면 그 자리가 이 원칙이 말하는 고칠 지점이다.

유지보수성은 **쓰지 않을 구조를 미리 만들어서 얻는 것이 아니다.** 그렇게 얻으려 하면 제1원칙과 충돌하고, 읽고 고칠 코드만 늘어난다.
지금 있는 것을 제자리에 놓는 것으로만 얻는다 — 그래서 다음 절이 "기능이 아니라 구조를 최적화한다"다.

### 먼저 — 기능이 아니라 구조를 최적화한다

**이 원칙은 미리 개발하라는 뜻이 절대 아니다.** 미래에 필요할지 모르는 기능·설정·확장 지점을 앞당겨 만드는 것과는 방향이 반대다.

지금 필요한 것만 만들되, 그것을 **올바른 자리에** 놓는 것이다. 만드는 양은 그대로 두고 놓는 자리를 바꾸는 일이다.

| 구조 최적화 — 이 원칙 | 미리 개발 — 오버엔지니어링 |
|---|---|
| 지금 쓰는 판단을 그 데이터를 가진 곳에 둔다 | 종류가 하나뿐인데 인터페이스·base class 를 미리 만든다 |
| 지금 있는 값의 타입을 정확히 적는다 | 지금 안 쓰는 필드·옵션을 "나중을 위해" 넣는다 |
| 지금 있는 분기를 소진 검사로 잠근다 | 아직 없는 종류를 위해 플러그인·전략 구조를 짠다 |
| 지금 쓰는 것에 도메인 이름을 붙인다 | 쓰이지 않는 접근자·훅 포인트를 미리 열어 둔다 |

**판단 기준은 하나다 — 코드 양이 늘어난다면 구조 최적화가 아니라 미리 개발이다.** 자리를 옮기는 것은 이 원칙이고, 없던 것을 짓는 것은 과설계다.

쓰이지 않을 설정 옵션·base class·추상화를 "나중을 위해" 만드는 것은 제1원칙과 **ponytail** 위반이며, 그 자체가 유지보수성을 **떨어뜨린다** — 아무도 쓰지 않는 구조도 읽고 고쳐야 할 코드다.

아래 다섯 갈래는 전부 "지금 있는 것을 어디에 놓을까"의 문제다. 하나도 "무엇을 더 만들까"가 아니다.

### 고칠 지점을 하나로 모은다

같은 판단·계산이 두 곳 이상에 복사되면, 요구가 바뀔 때 한쪽만 고쳐져 결과가 갈라진다. 판단은 그 데이터를 가진 객체 안에 둔다(**oop-responsibility-design**).

빠뜨린 한 곳을 나중에 찾는 비용이, 처음에 제자리에 두는 비용보다 늘 크다.

### 컴파일러가 고칠 곳을 짚게 한다

타입을 명시하고 `Any`·`Map<String, Any>`·`unknown`·`Record<string, unknown>` 으로 뭉개지 않으면, 필드가 바뀌는 순간 컴파일러(Kotlin·tsc)가 고쳐야 할 자리를 전부 알려준다.

사람이 `grep` 으로 사용처를 찾아야 하는 구조를 만들지 않는다. 프론트 DTO 필드는 서버가 주는 이름 그대로라는 규칙(rules.md MUST "계약")과 **api-contract** 스킬이 이 장치의 첫 고리다.

### 닫힌 값 집합은 소진 검사로 잠근다

enum·union 에 새 값이 생겼을 때 빠뜨린 분기가 컴파일 에러로 드러나게 한다(프론트 `switch` + `never` — **frontend-style**, 백엔드 else 없는 `when` — **kotlin-style**).

기본값으로 조용히 넘기면 새 종류가 늘 때마다 버그가 숨는다.

### 새 종류 추가가 '추가'로 끝나게 한다

종류가 늘 때마다 기존 `if`/`when` 을 고쳐야 한다면, 그 분기는 lookup 이나 타입으로 옮길 신호다.

단 **실제로 두 곳 이상에서 반복될 때만** 옮긴다 — 한 곳뿐인데 미리 나누는 것은 제1원칙 위반이다(**oop-responsibility-design** 의 전환 시점).

### 이름이 도메인을 닮게 한다

"할인 규칙을 바꿔 달라"는 요청을 받았을 때 어느 파일을 열지 바로 알 수 있어야 한다.

도메인에 없는 이름(`XxxManager`, `XxxHelper`, `utils.ts`)에 판단이 들어가면, 고칠 곳을 찾는 일이 코드 전체 읽기가 된다.

## 제3원칙 — 데이터의 흐름과 통제

하나의 값은 하나의 출처를 갖고, 그 형태는 경계를 지나도 변하지 않으며, 바뀌는 자리는 이름으로 드러난다.

세 갈래로 지킨다.

### 자료형 일치

프론트와 백엔드가 같은 스키마와 자료형을 공유한다. 경계에서 형 변환이나 필드 보정이 필요하다면, 그건 이미 정합성이 깨졌다는 신호다.

형태가 맞으면 "값이 없을 수도 있으니" 하는 방어 분기가 애초에 생기지 않는다.

홉별 구체 규칙은 공통 **api-contract** 와 프론트 **frontend-api** 에 있다.

### 단일 원본

하나의 값은 하나의 출처만 갖는다. 같은 데이터를 여러 곳에 복사해 두지 않고, 파생값은 저장하지 말고 원본에서 계산한다.

복사본이 생기는 순간 두 값이 어긋나고, 그걸 맞추려는 동기화 코드가 따라붙는다.

### 변경 지점의 통제

값이 바뀌는 곳은 명시적이고 한정적이어야 한다. 세터로 필드를 하나씩 열어 두면 객체가 스스로 규칙을 지킬 수 없고, 검증 책임이 호출부마다 흩어진다.

상태 변경은 도메인 동작 이름을 가진 메서드로만 연다 — `todo.status = Status.CANCELED` 가 아니라 `todo.cancel()` 이어야 취소 가능한지 검사할 자리가 생긴다.

게터도 변경 통로가 된다. 내부 컬렉션이나 가변 객체를 그대로 반환하면 호출자가 원본을 고칠 수 있고, 객체는 자기 상태가 바뀐 것을 알지 못한다.

값 객체는 불변으로 두고, 컬렉션은 복사본이나 읽기 전용 뷰로 반환한다. 판단이 필요하면 값을 꺼내 밖에서 계산하지 말고 객체에 물어본다(**oop-responsibility-design**).

이렇게 하면 "이 값이 왜 바뀌었는지"를 코드만 읽고 알 수 있다.

## 규칙 문서에도 그대로 적용된다

세 원칙은 코드에만 해당하지 않는다. 스킬·리뷰 규칙·안내 문서처럼 **규칙 자체를 고칠 때도 똑같이 적용된다.**

- **제1원칙** — 처음 보는 사람이 위에서 아래로 읽어 이해되게 쓴다. 줄 길이·빈 줄 같은 형식은 `CLAUDE.md` 의 문서 규칙을 따른다.

- **제2원칙** — 요청받은 문서만 고친다. 지나가다 발견한 어색한 서술은 고치지 말고 알린다. 원칙·규칙을 하나 바꾸면 그것을 가리키던 문서를 같은 변경에서 함께 맞춘다.

- **제3원칙 · 단일 원본** — 같은 규칙을 여러 문서에 복사하지 않는다. 정본 한 곳에 두고 나머지는 포인터로 가리킨다.

  규칙이 두 곳에 적히면 한쪽만 고쳐져 에이전트마다 다른 규칙을 본다 — 코드에서 파생값을 저장했을 때와 같은 문제다.

## 적발 신호

| 신호 | 어긋나는 원칙 |
|---|---|
| 지금 필요 없는 구조를 미리 만들었다 | 제1원칙 (상세는 **ponytail**) |
| "유지보수성"을 이유로 안 쓰는 확장 지점·옵션을 넣었다 | 제1원칙 — 제2원칙은 이것을 요구하지 않는다 |
| 요청과 무관한 코드까지 고쳤다 | 제2원칙 |
| 같은 판단·계산이 두 곳 이상에 복사되어 있다 | 제2원칙 · 고칠 지점을 하나로 |
| 타입을 뭉개 놓아 필드가 바뀌어도 컴파일러가 못 잡는다 | 제2원칙 · 컴파일러가 짚게 |
| 닫힌 값 집합을 분기하면서 소진 검사도 기본 처리도 없다 | 제2원칙 · 소진 검사 |
| 새 종류를 추가하려면 기존 분기를 고쳐야 한다 (2곳 이상 반복될 때) | 제2원칙 · 추가로 끝나게 |
| 경계에서 형 변환·필드 보정을 하고 있다 | 제3원칙 · 자료형 일치 |
| 같은 값이 두 곳에 저장되어 있고 맞추는 코드가 있다 | 제3원칙 · 단일 원본 |
| 원본에서 계산할 수 있는 값을 필드로 들고 있다 | 제3원칙 · 단일 원본 |
| 상태를 속성 대입으로 바꾼다 (`x.status = ...`) | 제3원칙 · 변경 지점의 통제 |
| 게터가 내부 컬렉션·가변 객체를 그대로 반환한다 | 제3원칙 · 변경 지점의 통제 |

영역별 구체 판정과 심각도는 각 영역 스킬의 "적발 신호" 표에 있다 — 백엔드 **kotlin-common**, 프론트 **frontend-common**, 설계 **oop-responsibility-design**.

머지 차단 여부는 `rules/code-review.md` 의 MUST 가 정한다.
