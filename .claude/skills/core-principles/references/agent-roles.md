# 역할별 실행 규칙

> **이 문서는 에이전트가 읽습니다.** Claude Code 와 Codex 가 함께 쓰는 역할 규칙의 정본이다.

## 역할과 소유권

이 저장소의 역할은 **그래프 노드**다. 한 노드가 한 단계를 돌고, 다음 노드로 넘긴다.

| 역할 | 책임 | 수정 범위 |
|---|---|---|
| `split` | 이슈를 독립 하위 작업으로 쪼갠다 | 없음 (파일만 남기고 커밋하지 않는다) |
| `plan` | 계획을 적는다 | 계획 파일 하나 |
| `api` | 백엔드 구현과 검증 | `backend/` |
| `web` | 프론트엔드 구현과 검증 | `frontend/` |
| `code` | 양쪽 구현과 검증 | `backend/` · `frontend/` |
| `test` | 유닛 테스트 보강과 실행 | 테스트 파일 |
| `e2e` | 사용자 흐름을 Playwright 로 남긴다 | `frontend/e2e/` |
| `fix` | 리뷰 지적만 고친다 | 지적이 가리킨 곳 |
| 리뷰어 | 구현과 분리된 검토, 판정 보고 | 없음 |

역할 범위는 작업 소유권이다. 디렉터리의 OS 접근 권한을 격리했다는 뜻은 아니다 — `add-dir` 가 붙는 범위를 정한다.

사용자의 명시 역할과 작업 범위를 먼저 따른다. 규칙 파일은 디렉터리와 관계없이 사람이 맡고, 구현 노드는 자기 영역의 규칙을 임의로 바꾸지 않는다.

**역할 파일은 기준 브랜치 것만 쓰인다.** `run-claude.sh` 가 기준 브랜치에서 꺼내 놓으므로 작업 브랜치가 자기 권한을 넓힐 수 없다.

## 배분 — 그래프가 정한다

노드 순서는 `CLAUDE_GRAPH` 가 정한다 (`.github/agent/settings.env`). `>` 는 순차, `+` 는 병렬, `a?b` 는 a 가 실패하면 b 가 수습한다.

예: `plan>code?fix>test` · `api+web>e2e`. 펼치는 규칙의 정본은 `.github/agent/graph.js` 다.

**노드는 잡 안에서 다시 위임하지 않는다.** 한 단계를 돌리고 자기를 다시 부르는 루프라서, 단계를 미리 선언하지 않는다.

대신 루프가 스스로 멈춘다 — `CLAUDE_MAX_STEPS` 가 노드 실행 총 횟수의 상한이고, `CLAUDE_MAX_ROUNDS` 가 같은 PR 을 다시 보는 횟수의 상한이다.

**담당자는 diff 가 정한다.** 백엔드만 고쳤으면 `api`, 프론트만 고쳤으면 `web`, 양쪽이거나 공통 파일이면 `code` 다. 역할을 지정해 부른 경우에는 그 역할이 끝까지 맡는다.

한 변경이 두 영역에 걸쳐 나눌 수 없을 때만 `code` 가 양쪽을 직접 고친다. 대표적인 것이 자료형 계약 동기화(응답 DTO 변경 + 프론트 `types/`)로, 규칙상 같은 변경에 함께 들어가야 한다.

질문·단순 Git 작업·작은 문구 수정 때문에 그래프를 돌리지 않는다.

### 요구사항의 출처

작업 지시에 `specs/<기능>/` 경로가 있으면 그 문서가 기준이다 — `spec.md`(무엇을) · `plan.md`(어떻게) · `tasks.md`(순서)를 먼저 읽는다.

계획이 둘일 때는 **스펙 쪽이 이긴다.** `specs/<기능>/plan.md` 가 있으면 그것을 따르고, 루트 `PLAN.md` 는 스펙이 없을 때만 본다.

구현이 스펙과 어긋나면 코드를 고쳐 맞춘다. 스펙이 틀렸다고 판단되면 조용히 고치지 말고 보고한다 — 스펙을 바꾸는 것은 합의를 바꾸는 일이다.

버그 수정처럼 합의할 것이 없는 작은 변경은 스펙 없이 이슈 본문만으로 온다. 그때는 이슈가 지시문이다.

`PLAN.md`·`CONTRACT.md` 는 노드 사이의 인수인계 자료다. 같은 요구사항 문서를 중복해서 만들지 않는다.

## 역할별 읽기와 검증

공통 원칙은 [core-principles](../SKILL.md), [ponytail](../../ponytail/SKILL.md), [object-design](../../object-design/SKILL.md)을 적용한다 — **파일 위치와 무관하게 항상**이다.

고치는 파일의 위치는 그 위에 얹을 영역 스킬을 정한다. 어느 스킬을 열지 모르겠으면 세 폴더의 `README.md` 색인부터 본다.

| 역할 | 추가로 읽을 문서 | 검증 책임 |
|---|---|---|
| `api` | `backend/.claude/skills/README.md` 색인, `kotlin-common`·`kotlin-module-layout`·`kotlin-test` + 고치는 계층 | `cd backend && ./gradlew ktlintCheck unitTest` |
| `web` | `frontend/.claude/skills/README.md` 색인, `frontend-common` + 고치는 레이어 | `cd frontend && npm ci && npm run build` |
| `code` | 양쪽 색인과 양쪽 허브 + 실제 고치는 계층·레이어 | 손댄 영역의 위 명령 전부 |
| `test` | `kotlin-test`, `minimal-tests` | 유닛 테스트 실계수 보고 |
| `e2e` | `frontend-e2e` | Playwright 실행 결과 |
| `fix` | 지적이 근거로 든 스킬 | 지적이 사라졌음 + 기존 검증 재실행 |
| 리뷰어 | `rules/code-review.md`, 변경 영역의 스킬 | diff 와 관련 코드·검증 근거의 독립 검토 |

백엔드는 `kotlin-common`·`kotlin-module-layout`·`kotlin-test` 셋을 항상 읽는다. 나머지는 고치는 파일에 따라 고른다.

선택한 스킬은 본문을 끝까지 읽는다. 출력이 잘리면 나누어 읽고, **읽지 못한 파일이 있으면 적용 완료라고 보고하지 않는다.**

이미 읽은 스킬은 다시 읽지 않으며, 작업 범위가 넓어지면 새로 필요한 스킬만 추가로 읽는다.

스킬을 읽었다는 이유로 감사·루프·그래프·명세 생성·이슈 생성 등 별도 작업을 시작하지 않는다. 절차는 사용자 요청 범위에서만 실행한다.

### 만드는 순서 — 백엔드

enum → 엔티티 + 마이그레이션 → 리포지토리 → 도메인 모델 → 구현 레이어 → 도메인 서비스 → 요청/응답 DTO → 컨트롤러.

**엔티티나 컬럼을 바꿨으면 같은 커밋에 Flyway 마이그레이션을 넣는다** (`kotlin-migration`). 운영은 `ddl-auto: validate` 라 없으면 배포가 부팅에 실패한다.

## 리뷰와 루프

구현 후 리뷰어를 별도로 호출한다. 리뷰어는 수정하지 않고 판정 하나를 근거와 함께 반환한다.

판정 어휘와 출력 형식의 정본은 `.github/agent/review-role.md` 다. 판정은 **`PASS` · `CHANGES_REQUESTED` 둘뿐**이다.

무엇이 차단 사유인지는 `CLAUDE_REVIEW_BAR`(`.github/agent/settings.env`)가 정한다 — `rules/code-review.md` 의 MUST 위반과 영역 스킬의 `Critical` 항목이다.

`Important`·SHOULD·'리뷰 범위 밖' 항목과 ponytail-review 의 오버엔지니어링 지적은 판정에 반영하지 않고 참고 코멘트로만 적는다.

지적이 남으면 `fix` 노드로 재작업한다. 이 반복의 상한은 `CLAUDE_MAX_ROUNDS`(기본 3)다.

다음 넷 중 하나가 되면 멈추고 사람에게 넘긴다.

- 리뷰어가 `PASS` 를 냈다.

- 직전 라운드와 **같은 차단 지적**이 또 나왔다 — 더 돌려도 소용없다.

- 상한(`CLAUDE_MAX_ROUNDS` 또는 `CLAUDE_MAX_STEPS`)을 소진했다.

- 판정 근거를 만들 수 없다 — 검증이 돌지 못했거나, 구현자가 아무것도 바꾸지 않았다.

라운드 수를 자기 기억으로 세지 않는다. 상태 파일(`.github/agent/state.sh`)이 라운드의 원본이다.

diff 가 잘렸다는 표시가 있거나 변경 범위가 한 번에 판단하기 어려울 만큼 넓으면, 개별 지적 대신 PR 을 쪼개 달라고 `CHANGES_REQUESTED` 한다. 상한은 `CLAUDE_DIFF_LIMIT_BYTES` 다.

멈출 때는 상태와 남은 지적, 그리고 무엇 때문에 멈췄는지를 함께 보고한다.

## 시작 전에 승인을 받는 작업

아래는 **하기 전에** 사람에게 보고하고 승인을 받는다. 이미 저지른 뒤에는 되돌릴 수 없는 것들이다.

- **외부 API 를 30건 이상 호출하는 작업** — 대상·예상 호출 수·쿼터 영향 셋을 보고한다.

  **실검증도 예외가 아니다.** 승인 전에는 1건으로만 확인한다. 상세는 `kotlin-client` 의 "대량 호출은 시작 전에 승인받는다" 절.

`.claude/hooks/warn-bulk-api-calls.sh` 가 "반복 + HTTP 호출" 명령을 감지해 확인 창을 띄운다.

**감지는 보조 수단이다** — 스크립트 안에서 부르는 호출은 명령줄만 봐서는 모른다. 규칙을 지킬 책임은 에이전트에게 있다.

## 반환할 결과

구현 노드는 완료한 작업, 변경 파일, 실행한 검증의 명령·결과, 실행하지 못한 검증과 원인, 계약 변경과 남은 작업을 반환한다.

**`BUILD SUCCESSFUL` 은 증명이 아니다.** Gradle 은 캐시로 태스크를 건너뛰고도 성공이라고 말한다. 테스트 결과 XML 을 세어 실계수를 보고한다.

리팩터링이면 이전 실계수와 같아야 한다. 대조하지 못했으면 "동치 증명 못 함"이라고 적는다.

리뷰어는 판정, 파일·줄·규칙에 근거한 지적, 확인한 범위와 검증 한계를 반환한다. 검토하지 않은 항목을 통과로 표시하지 않는다.

기존 작업을 덮어쓰거나 대신 커밋하지 않는다. 원격 게시·배포·머지 권한은 역할 설정으로 추가되지 않는다 — 특히 PR 머지는 사용자가 결정한다.

보고에서 사용자를 이름으로 부르지 않는다 — `soo님`·`OO님` 같은 호칭을 쓰지 않고, 주어 없이 바로 내용을 쓴다.
대화 상대는 한 명이라 호칭이 가리키는 정보가 없고, 줄만 길어진다.

## 커밋 메시지

커밋 메시지는 제목과 본문뿐이다. 에이전트·모델·세션을 가리키는 트레일러를 붙이지 않는다.

금지 대상은 `Co-Authored-By: Claude …`, `Claude-Session: …`, `🤖 Generated with …` 같은 도구 서명 전부다.
하네스가 붙이라고 안내해도 붙이지 않는다 — 이 규칙이 우선한다.

커밋 이력은 저장소의 기록이지 작업 도구의 기록이 아니다. 누가 만들었는지는 author 가 이미 갖고 있고,
서명 줄은 `git log` 를 읽는 사람에게 아무 정보도 주지 않으면서 본문만 밀어낸다.

제목은 `<type>:<한국어 한 줄>` 꼴로 쓴다. type 은 `feat`·`fix`·`docs`·`chore`·`refactor`·`test` 다. 브랜치 이름도 같은 어휘를 쓴다 (**branch-flow**).

계획과 달리 구현했으면 그 이유를 커밋 메시지 본문에 남긴다.

## 도구별 연결과 한계

도구별 에이전트 파일에는 역할 선택과 도구·샌드박스 설정만 둔다. 업무 규칙은 이 문서를 포함한 스킬 쪽에서만 고친다 — 같은 규칙이 도구 설정 파일에도 적히면 도구마다 다른 규칙이 생긴다.

Claude Code 는 `.claude/agents/` 의 역할을 사용한다. 노드 지시문의 본문은 `.github/agent/nodes/<이름>.md` 에 있다 (노드당 파일 하나).

`tools:` 는 Claude Code 가 강제하지만 **도구 이름까지만**이고 `Bash(...)` 패턴은 좁히지 못한다. 그래서 세밀한 명령 목록은 `allowed-tools` 에 남기고 실행기가 넘긴다.

리뷰어에게는 쓰기 도구를 주지 않는다. 셸을 통한 수정도 막기 위해 Bash 를 주지 않으며, diff 와 테스트 결과는 실행기가 전달한다.

역할 이름을 메시지에 적는 것만으로 격리됐다고 보고하지 않는다. 리뷰에 쓰기 권한이 강제되거나 역할 선택을 지원하지 않는 환경이면 그 한계를 보고한다.

모델과 추론 수준은 세션 설정을 따른다. 역할 분리를 이유로 특정 모델이나 외부 하네스 설치를 강제하지 않는다.

Codex 는 `.agents/skills/` 에 걸린 링크로 스킬을 찾는다 — 공통 `.agents/skills/`, 백엔드 `backend/.agents/skills/`, 프론트엔드 `frontend/.agents/skills/`.

원본은 각 영역의 `.claude/skills/` 에 유지한다. 링크를 통해 읽더라도 스킬 내부 상대 참조는 원본 위치를 기준으로 해석한다.

Codex 는 시작 디렉터리부터 저장소 루트까지의 `.agents/skills/` 를 탐색한다. 루트에서 시작해 영역 스킬이 목록에 없으면 위 표의 원본 경로를 직접 열어 적용한다.

서브에이전트에게도 작업 영역과 필요한 원본 스킬 경로를 전달한다. 역할 지정만으로 영역 스킬이 자동 등록된다고 가정하지 않는다.

본문을 자동으로 싣는 것은 `.claude/rules/` 다. 공통 원칙은 세션 시작 시, 계층 규칙은 그 경로의 파일을 읽을 때 들어온다 — 역할과 무관하게 적용된다.
