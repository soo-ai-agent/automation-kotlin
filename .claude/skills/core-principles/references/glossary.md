# 용어 사전

규칙 문서와 리뷰 코멘트에서 쓰는 낱말을 하나의 뜻으로 고정한다.

같은 낱말이 여러 뜻으로 쓰이면 읽는 사람이 문맥으로 추측해야 하고, 추측이 갈리는 순간 규칙이 규칙이 아니게 된다.

**규칙 문서를 쓸 때는 이 표의 낱말만 쓴다.** 표에 없는 은유를 새로 만들지 않는다.

## 계약 — 단독으로 쓰지 않는다

`계약` 은 이 저장소에서 다섯 가지를 가리켰다. 항상 수식어를 붙여 어느 것인지 드러낸다.

| 쓸 말 | 뜻 | 정본 |
|---|---|---|
| **자료형 계약** | 도메인 모델 → 응답 DTO → 프론트 `types/` 세 홉의 필드 이름·타입·널 허용이 일치하는 것 | api-contract |
| **입력 계약** | 요청 DTO 가 받기로 한 필드와 검증 규칙 | kotlin-dto |
| **출력 계약** | 응답 DTO 가 내보내기로 한 JSON 필드와 포맷 | kotlin-dto |
| **공개 계약** | 바깥이 이름과 의미에 의존하는 것 — public API 경로·상태코드, DB 컬럼, 외부에서 쓰는 함수 | `rules/code-review.md` MUST |
| **API 명세** | api 노드가 `CONTRACT.md` 에 적는 이번 작업의 엔드포인트 목록 | `.github/agent/nodes/api.md` |

프레임워크(Spring·JPA)가 강제하는 규칙은 계약이 아니라 **런타임 불변 조건**이라고 쓴다 (kotlin-config·kotlin-entity).

리뷰어의 출력 형식은 계약이 아니라 **판정 형식**이라고 쓴다 (`.github/agent/review-role.md`).

## 리뷰 낱말

| 쓸 말 | 뜻 |
|---|---|
| **적발 신호** | 스킬의 표에 적힌, 리뷰에서 찾아야 할 코드 패턴 |
| **심각도** | 적발 신호 하나에 붙는 등급 — `Critical` · `Important` · `Code Smell` |
| **차단 사유** | 머지를 막는 근거. `rules/code-review.md` 의 MUST 위반과 심각도 `Critical` 뿐이다 |
| **판정** | 리뷰어가 내는 결론 — `PASS` · `CHANGES_REQUESTED` 둘뿐이다 |
| **판정 형식** | 판정을 적는 출력 규격 (`.github/agent/review-role.md`) |

**`게이트`·`관문`·`문턱` 은 쓰지 않는다.** 머지를 막는 것은 `차단 사유`, 실행을 가르는 것은 `조건` 이다.

**`APPROVED`·`BLOCKED` 는 이 저장소의 판정 어휘가 아니다.** 통과는 `PASS` 다.

## 계층과 레이어 이름

낱말이 갈리면 어느 파일을 여는지가 달라진다. 아래 이름만 쓴다.

| 영역 | 쓸 말 | 뜻 |
|---|---|---|
| 백엔드 | **컨트롤러** | HTTP 를 받는 자리 (`controller`) |
| 백엔드 | **도메인 서비스** | 유스케이스와 트랜잭션 경계 (`domain service`) |
| 백엔드 | **구현 레이어** | Finder·Appender 등 재사용 단위 (`implement`) |
| 백엔드 | **리포지토리** | 저장과 조회 (`repository`) |
| 백엔드 | **엔티티** | JPA 가 매핑하는 저장 타입 |
| 백엔드 | **도메인 모델** | 구현 레이어 위로 올라가는 불변 타입 |
| 프론트 | **화면** | `screens/` — `페이지` 라고 쓰지 않는다 |
| 프론트 | **훅** | `hooks/` |
| 프론트 | **서비스** | `services/` — 백엔드의 도메인 서비스와 구분해 문맥을 붙인다 |

`서비스` 가 양쪽에 있으므로 **어느 쪽인지 드러나지 않는 자리에서는 `도메인 서비스`·`프론트 서비스` 로 쓴다.**

## 자주 쓰는 은유

| 쓸 말 | 뜻 | 쓰지 말 것 |
|---|---|---|
| **정본** | 같은 내용이 여러 곳에 보일 때, 고쳐야 하는 단 하나의 원본 | 원본, 소스 오브 트루스 |
| **수직 슬라이스** | 한 도메인이 계층을 관통해 갖는 파일 한 벌 (엔티티→리포지토리→구현→도메인 서비스→컨트롤러) | 세로 묶음 |
| **판단 축** | 분기가 보고 있는 하나의 관점 (상태·권한·시간 등) | 기준, 차원 |
| **단일 창구** | 같은 일을 하는 통로를 하나로 모은 것 (알림은 `notify` 하나) | 게이트웨이, 엔트리포인트 |
| **실계수** | 실제로 실행된 테스트의 개수. `BUILD SUCCESSFUL` 이 아니라 결과 XML 을 세어 얻는다 | 테스트 수 |
| **동치 증명** | 리팩터링 전후의 동작이 같다는 근거 (실계수·매핑 목록·응답 본문 대조) | 검증했음 |

## 레거시를 가리킬 때

버전이 있는 것은 **버전을 적는다.** "구식", "옛날 방식" 처럼 시점에 기대는 말을 쓰지 않는다.

`javax.persistence 패키지` · `Spring Boot 2.x 설정` · `React 클래스 컴포넌트` 처럼 무엇의 어느 버전인지 드러낸다.
