# 최소한의 테스트

테스트는 **깨졌을 때 알려주는 장치**다. 많을수록 좋은 것이 아니라, 깨지는 것을 잡아야 값을 한다.

이 문서가 새로 정하는 것은 셋이다 — **언제 쓰나 · 어디에 두나 · 무엇을 검증하나.** 나머지는 기존 정본을 따른다.

| 이미 정해져 있는 것 | 정본 |
|---|---|
| 테스트 함수 하나의 범위 (검증 목적 하나) | **core-principles** "테스트 함수의 범위" |
| 얼마나 적게 만들 것인가 (프레임워크·픽스처 금지) | **ponytail** "검증 없는 게으른 코드는 미완성" |
| 코틀린 유닛 테스트 문법·MockK 스텁 범위·레이어별 대상 | **kotlin-test** |
| Playwright 선택자·대기·다이얼로그 처리 | **frontend-e2e** |
| 요청받지 않은 테스트 추가 제안은 리뷰 대상 아님 | `rules/code-review.md` |

## 언제 쓰나

**판정은 한 문장이다 — 이 로직이 조용히 틀리면 누가 알아채는가.** 아무도 못 알아채면 테스트를 쓴다.

쓴다:

- 분기·루프·파싱이 있는 로직. 조건이 둘 이상이면 경계에서 틀린다

- 돈·권한·삭제처럼 틀렸을 때 되돌리기 어려운 경로

- **고친 버그.** 같은 버그가 돌아오면 실패하는 테스트 하나를 남긴다 — 이것이 가장 값싼 테스트다

- 이름으로 주장한 조건 (`isEditable` 같은 술어). 테스트가 없으면 그 이름은 검증되지 않은 주장이다

- 엔티티 행위 메서드의 불변식. `require`·`check` 로 막은 조건은 그 조건이 깨졌을 때 실패하는 테스트가 있어야 막은 것이다

쓰지 않는다:

- 한 줄짜리 위임·전달 함수. 컴파일러가 이미 잡는다

- 프레임워크·라이브러리가 보증하는 동작 (JPA 가 저장하는지, 스프링이 라우팅하는지)

- 요청에 없는 기능의 테스트. 만들지 않은 것을 검증하지 않는다

- 실행할 수 없는 환경에서의 "형식만 테스트" — 돌지 않는 테스트는 통과로 오해되는 장식이다

- **코드를 고쳐 없앤 것을 다시 감시하는 테스트.** 요청이 "아예 하지 마라"였고 그렇게 고쳤다면 거기서 끝이다.
  그 코드가 되살아나는지 소스를 훑어 보는 테스트를 덧붙이지 않는다 — 요청에 없던 장치이고, 앞으로의 모든 수정을 감시하는 비용만 남는다.

  판정: **이 테스트가 잡는 것이 "지금 코드의 버그"인가, "미래에 누가 규칙을 어기는 일"인가.** 뒤쪽이면 쓰지 않는다.
  규칙을 강제할 값이 정말 있다고 판단되면 테스트를 덧붙이지 말고 그 판단을 먼저 알린다(**core-principles** 제 2원칙 · 손대는 범위).

## 어디에 두나

이 저장소가 실제로 쓰는 자리다. 새 관례를 만들지 말고 여기에 맞춘다.

| 대상 | 위치 | 이름 | 실행 |
|---|---|---|---|
| 백엔드 유닛 | 대상과 같은 패키지의 `src/test/kotlin/…` | `<대상>Test.kt` | `cd backend && ./gradlew test`(태스크 이름은 `./gradlew tasks` 로 확인) |
| 프론트 화면 흐름 | `frontend/e2e/` | `<도메인>.spec.ts` | `cd frontend && npm run test:e2e` |
| 하네스·스크립트 | `tests/cases/<영역>/` | `<상황>.case`·`<상황>.diff` | `tests/run.sh` |

파일 이름의 `<대상>` 은 검증하는 대상의 이름을 그대로 쓴다 — `TodoAppenderTest.kt` 는 `TodoAppender` 를 검증한다. 다르면 검색이 끊긴다.

**테스트는 저장소 트리 안에 둔다.** 임시 폴더에 만들어 돌리고 지우면 다음 사람에게 남는 것이 없다.

**프론트엔드는 유닛 테스트를 두지 않는다.** 화면 흐름은 E2E 로 검증한다 (`rules/code-review.md` 테스트 절).

## 무엇을 검증하나

**검증 범위는 이번에 작성한 코드까지다.** 테스트는 내가 쓴 코드에 이상이 있나 없나를 보는 장치이지, 그 코드가 부르는 남의 코드가 맞는지 보는 장치가 아니다.

그래서 이번 변경이 만들거나 고친 함수·분기·판정만 대상으로 삼는다. 호출한 라이브러리·프레임워크·이미 있던 다른 모듈의 동작은 그 자리에서 다시 검증하지 않는다 — 그것들이 틀렸다면 그쪽 변경에서 잡을 일이다.

범위를 넘기면 대가가 분명하다. 남의 코드가 바뀔 때마다 내 테스트가 깨지고, 정작 내 코드의 버그는 그 소음에 묻힌다. 테스트가 붙잡고 있는 것이 무엇인지도 이름만 보고는 알 수 없게 된다.

같은 이유로, 요청 범위 밖에서 발견한 남의 코드의 결함은 테스트를 덧붙여 덮지 말고 알린다(**core-principles** 제 2원칙 · 손대는 범위).

**결과를 검증하고 과정을 검증하지 않는다.** 내부 호출 순서·private 이름을 확인하는 테스트는 리팩터링할 때마다 깨지면서 아무 버그도 잡지 못한다.

사용자 기능은 결과를 바꾸는 입력값을 골라 검증한다. 정상값·경계값·미응답·잘못된 값 중 해당 기능에 의미 있는 경우를 고른다.

같은 판단의 입력값만 달라지면 `@ParameterizedTest` 로 묶고, 검증 목적이 달라지면 메서드를 나눈다. 가능한 모든 조합을 무작정 늘리지 않는다.

경계부터 고른다. 값 하나를 고를 수 있다면 그 값은 경계값이다.

- 빈 것 — 빈 목록, 빈 문자열, 결과 0건

- 하나 — 원소 1개에서 규칙이 성립하는가

- 넘는 것 — 중복 저장, 없는 id 조회, 허용 범위 밖 입력

- 되돌아오는 것 — 실패한 뒤 상태가 남아 있지 않은가

정상 하나만 있는 테스트는 절반이다. **실패 경로를 최소 하나 넣는다** — 서비스라면 상태코드별 분기, 도메인이라면 불변식 위반.

## 어떻게 쓰나

준비 → 행동 → 검증 세 덩어리가 눈에 보이게 쓴다. 세 덩어리를 한 줄로 압축하지 않는다(제 1원칙 · 단순함 최우선).

테스트 이름은 **무엇이 참인지**를 문장으로 쓴다. 백틱 이름을 쓴다 — `fun saveTest()` 가 아니라 `` fun `같은 날짜에 저장하면 기존 노트를 덮어쓴다`() `` 다.

준비가 길어지면 그 자체가 설계 신호다 — 객체 하나를 만드는 데 열 줄이 필요하면, 그 객체가 너무 많은 것을 알고 있다(**object-design**).

이전 테스트가 남긴 상태에 기대지 않는다. 테스트 순서를 바꿔도 결과가 같아야 한다.

## 코틀린 유닛 테스트 — 메서드는 작게, 의존은 적게

**메서드 하나에는 그 목적을 입증하는 검사만 둔다.** 목적과 무관한 확인(다른 필드, 옆 기능, 지나가는 김에 본 값)을 얹지 않는다.

개수를 세어 자르라는 뜻이 아니다 — 하나의 목적을 입증하는 데 필요한 단언은 여럿이어도 함께 둔다(**core-principles** "테스트 함수의 범위"). 잘라내는 기준은 **개수가 아니라 목적**이다.

**단순하게 쓴다.** 테스트를 읽는 데 다른 파일을 열어야 하면 이미 복잡하다.

- 상속으로 테스트 베이스 클래스를 쌓지 않는다. 공통 준비가 필요하면 그 파일 안의 작은 함수 하나로 둔다

- 반복 케이스는 `@ParameterizedTest` 로 한 메서드에서 돌리되, 케이스마다 다른 것을 검증하게 되면 메서드를 나눈다

- 기대값을 계산하거나 시나리오를 분기하는 조건문·반복문을 테스트 안에 넣지 않는다. 입력·기대값 표를 돌리는 매개변수 반복은 허용한다

### 단위 테스트는 최소한의 의존성으로

**DB·네트워크·스프링 컨텍스트 없이 도는 것이 단위 테스트다.** 그것들이 필요하면 단위 테스트가 아니라 통합 테스트다.

| 대상 | 이렇게 | 이러지 않게 |
|---|---|---|
| 엔티티 행위 메서드 | 인스턴스를 직접 만들어 호출 | 영속성 컨텍스트를 열고 DB 에 넣었다 뺀다 |
| 구현 레이어(Finder·Appender) | 리포지토리만 `mockk()` 로 스텁 | `@SpringBootTest` 로 컨텍스트 부팅 |
| 도메인 서비스 흐름 | 구현 레이어 자리에 필요한 메서드만 가진 가짜 | 컨테이너를 띄워 진짜 빈을 주입 |
| 순수 계산·판정 | 값을 넣고 반환값 확인 | 컨트롤러를 통해 HTTP 로 호출 |

`mockk` 는 **진짜 객체를 만들기 어려울 때만** 쓴다. 몇 줄로 만들 수 있는 것은 진짜로 만든다 — mock 은 호출 방식을 굳혀서 리팩터링을 막고, 그러면서 정작 결과는 검증하지 않는다.

스텁 범위는 **그 테스트가 실제로 지나가는 호출까지**다. 쓰지 않는 `every` 를 미리 깔아 두지 않는다 (상세는 **kotlin-test**).

JUnit5 + MockK + AssertJ 로 되는 일에 새 테스트 라이브러리를 더하지 않는다(**ponytail**).

## 실행했다는 증명

**`BUILD SUCCESSFUL` 은 증명이 아니다.** Gradle 은 캐시로 태스크를 건너뛰고도 성공이라고 말한다.

**캐시는 양방향으로 거짓말한다** — 소스를 고쳤는데 옛 클래스가 남아 멀쩡한 코드가 실패하기도 하고, 망가진 코드가 통과하기도 한다. 판정이 걸린 실행과 아래 변이 검사에는 `--rerun-tasks` 를 붙인다.

테스트 결과 XML(`build/test-results/`)을 세어 **실계수**를 보고한다. 리팩터링이면 이전 실계수와 같아야 한다.

**바꾼 규칙마다 변이를 넣어 테스트가 깨지는지 본다.** 조건을 `true` 로, 상수를 다른 값으로 바꾸고 돌렸을 때 실패가 0건이면 그 규칙에는 테스트가 없는 것이다.

이것은 `core-principles` 의 "통과하는 검사와 아무것도 검사하지 않는 검사는 겉보기가 같다"를 테스트에 적용한 것이다.

## E2E — 목적 하나, 최소 검증

E2E 는 느리고 잘 깨져서 군더더기의 대가가 가장 크다. 위의 "무엇을 검증하나"를 화면 테스트에 그대로 적용한다.

- **도구가 이미 해 주는 일을 테스트에 적지 않는다.** Playwright 의 `screenshot: "only-on-failure"` 가 실패 캡처를 남기므로,
  통과 경로에 `page.screenshot(...)` 을 수동으로 넣지 않는다. 실패했을 때만 필요한 증거를 늘 만들 이유가 없다.

- **"없어진 문구가 없는지" 확인하는 단언은 오래 못 간다.** 지운 문구는 enum·코드에서 이미 사라졌으므로
  그 검사는 영원히 참이고, 테스트 이름만 과거 작업 이력으로 남는다. 지우고 테스트 이름도 현재 동작으로 고친다.

- **목적 밖 존재 확인을 얹지 않는다.** "로고를 눌러 초기화된다"를 검증하는 테스트라면 누른 뒤의 결과만 본다 —
  누르기 전에 그 버튼이 보이는지, 옆 버튼이 없는지까지 확인하면 목적이 셋이 된다.

- 여러 화면을 거쳐야 하는 준비는 그 파일 안의 작은 helper 하나(`reachAgeQuestion(page)`)로 두고, 테스트 본문에는
  행동과 검증만 남긴다. helper 안에 검증을 숨기지 않는다.

## 하지 않는 것

- 커버리지 숫자를 목표로 삼지 않는다. 덮인 줄 수는 깨짐을 잡는 능력과 다르다

- 테스트를 맞추려고 제품 코드를 비틀지 않는다 (테스트 전용 인자·플래그 금지)

- 실패하는 테스트를 `@Disabled` 나 주석으로 덮지 않는다. 고치거나, 왜 지금 못 고치는지 적고 지운다

- 통과시키려고 단언을 약화하지 않는다 (`rules/code-review.md` MUST)

- 요청 범위 밖의 기존 테스트를 지우지 않는다 (`rules/code-review.md` 범위 규율)

## 적발 신호

| 신호 | 문제 |
|---|---|
| 테스트 하나가 생성·수정·삭제를 연달아 검증 | 목적이 여럿 — core-principles 의 범위 규칙 위반 |
| 이번 변경이 만들지 않은 코드(라이브러리·기존 모듈)의 동작을 검증 | 검증 범위 초과 — 남의 코드가 바뀔 때마다 깨지고 내 버그는 못 잡는다 |
| 정상 경로만 있는 테스트 | 실패 경로가 없어 방어 코드가 검증되지 않는다 |
| 내부 호출 횟수·private 이름을 확인 | 과정 검증 — 리팩터링마다 깨지고 버그는 못 잡는다 |
| 이전 테스트의 결과에 기대는 테스트 | 순서를 바꾸면 실패한다 |
| 저장소 밖에서 돌리고 지운 검증 | 다음 사람에게 남는 것이 없다 |
| 고친 버그에 회귀 테스트가 없다 | 같은 버그가 돌아와도 아무도 모른다 |
| 단위 테스트가 DB·스프링 컨텍스트·네트워크를 요구한다 | 단위 테스트가 아니라 통합 테스트다 |
| 쓰지 않는 `every` 스텁이 깔려 있다 | 실제로 지나가지 않는 경로를 검증한 것처럼 보인다 |
| 테스트가 조건문·반복문으로 기대값이나 실행 시나리오를 계산한다 (매개변수 입력 표 제외) | 테스트가 가진 로직도 틀릴 수 있다 |
| 몇 줄이면 만들 수 있는 객체를 `mockk` 로 대체 | 호출 방식이 굳어 리팩터링을 막는다 |
| `BUILD SUCCESSFUL` 만 보고 통과로 보고 | 캐시로 건너뛴 것과 구분되지 않는다 — 실계수를 센다 |
| 돌릴 수 없는 환경에 남긴 테스트를 "통과"로 보고 | 실행하지 않은 것을 통과로 적지 않는다 |
| 테스트 폴더가 어느 tsconfig 에도 안 들어가 있다 | 타입 오류가 조용히 통과한다 — 검사 대상에 포함시킨다 |
| 통과 경로에 수동 스크린샷·로그를 남긴다 | 도구가 실패 시 이미 남긴다 — 중복이다 |
| 이미 지운 문구가 없는지 확인하는 단언 | 영원히 참이라 아무것도 못 잡는다 |
| 코드를 고쳐 없앤 것을 소스 훑어 감시하는 테스트 | 요청에 없던 장치 — 잡는 것이 버그가 아니라 미래의 규칙 위반이다 |

## 체크리스트

- [ ] 이 로직이 조용히 틀렸을 때 이 테스트가 실패하는가

- [ ] 테스트 이름이 무엇이 참인지 말하는가

- [ ] 검증 목적이 하나인가 (여럿이면 메서드를 나눈다)

- [ ] 검증 대상이 이번에 작성·수정한 코드로 한정되는가

- [ ] 실패 경로가 최소 하나 있는가

- [ ] 목적과 무관한 검사를 얹지 않았는가 (개수가 아니라 목적 기준)

- [ ] 단위 테스트가 DB·스프링 컨텍스트·네트워크 없이 도는가

- [ ] 위 표의 위치·이름 관례를 따랐는가

- [ ] 실제로 실행하고 **실계수**를 확인했는가 (실행하지 못했으면 그 사실을 결과에 적었는가)
