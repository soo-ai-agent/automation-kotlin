# 브랜치 흐름

브랜치는 **작업 하나를 담는 그릇**이다. 그릇이 무엇을 담는지 이름으로 보이고, 다 담으면 비운다.

5대 원칙(**core-principles**)에 종속된다 — 특히 제 2원칙(최소 수정·무파괴)의 "손대는 범위는 요청이 지목한 곳까지다"가 브랜치 크기를 정한다.

## 한눈에

- **이름** — `<type>/<주제-kebab>`. type 은 커밋 메시지와 같은 어휘를 쓴다

- **범위** — 브랜치 하나에 목적 하나. 리팩터링과 동작 변경을 한 브랜치에 섞지 않는다

- **최신화** — 대상 브랜치를 내 브랜치로 **병합**한다. 올라간 이력을 rebase 로 갈아엎지 않는다

- **재작업** — 리뷰 지적은 새 브랜치가 아니라 **같은 브랜치에 push** 한다

- **정리** — 머지되면 지운다. 남은 브랜치는 남은 작업으로 읽힌다

## 이름 — 무엇을 하는 브랜치인지 이름만 보고 안다

`<type>/<주제-kebab>` 로 쓴다. type 은 커밋 메시지의 어휘를 그대로 쓴다 — `feat`·`fix`·`docs`·`chore`·`refactor`·`test`.

| 좋은 이름 | 나쁜 이름 | 왜 |
|---|---|---|
| `feat/user-daily-note` | `feature-1` | 무엇을 만드는지 없다 |
| `fix/stale-response-guard` | `fix` | 무엇을 고치는지 없다 |
| `refactor/note-editor-hooks` | `soo-work` | 사람 이름은 내용을 말하지 않는다 |
| `chore/drop-legacy-column` | `tmp`·`test2` | 지워도 되는지 판단할 수 없다 |

주제는 영문 kebab-case 로 쓴다. 한글 브랜치 이름은 도구·URL 에서 깨지는 곳이 있다.

**`claude/issue-N` 은 자동화가 예약한 모양이다.** 사람이 손으로 그 이름을 쓰지 않는다 — 디스패처와 리뷰어가 이 접두사로 자동 머지·청소 대상을 판별한다(`.github/automation-spec.md`).

자동 머지에는 조건이 둘이다 — head 브랜치가 `claude/issue-N` 이고, 그 이슈에 `claude-made` 라벨이 있을 때뿐이다. 사람 브랜치의 PR 은 이름 규칙으로 제외된다.

### 에이전트가 만든 브랜치는 에이전트가 관리한다

사람이 `claude/issue-N` 에 직접 push 하지 않는다. 커밋을 얹거나 기본 브랜치를 대신 병합해 주면, 그 브랜치가 무엇을 겪었는지 자동화가 모르는 채로 다음 노드가 돈다.

**설정과 도구는 항상 기본 브랜치에서 읽는다** — `settings.env`·`nodes/*.md`·`run-claude.sh` 는 전부 `git show origin/$DEF:...` 로 꺼낸다.

그래서 기본 브랜치에서 규칙을 고치면 이미 떠 있는 브랜치도 다음 실행부터 새 규칙으로 돈다. 다만 **스킬 본문은 체크아웃된 작업 브랜치에서 읽히므로**, 스킬을 고쳤으면 그 브랜치가 기본 브랜치를 병합해야 반영된다.

브랜치가 막혀 사람의 손이 필요해 보이면, 밀어 주기 전에 **왜 에이전트가 스스로 못 했는지**를 먼저 본다. 대개 도구 권한이나 규칙이 빠진 것이고, 그것을 기본 브랜치에서 고치면 다음 실행이 알아서 가져간다.

## 범위 — 브랜치 하나에 목적 하나

**브랜치의 목적을 한 문장으로 말할 수 없으면 이미 두 브랜치다.** 커밋을 나누는 기준과 같다.

- 리팩터링과 동작 변경을 한 브랜치에 섞지 않는다 (`rules/code-review.md` 범위 규율).

- 지나가다 발견한 문제는 그 브랜치에서 고치지 말고 알린다 — 고치면 리뷰어가 "이 변경이 요청에 꼭 필요한가"를 판단할 수 없다.

- 계약 변경(백엔드 응답 DTO ↔ 프론트 `types/`)처럼 **양쪽을 함께 바꿔야 깨지지 않는 것**은 한 브랜치에 담는다. 이건 범위 확장이 아니라 필요한 변경이다.

- 엔티티·컬럼 변경과 그 **Flyway 마이그레이션**도 한 브랜치다. 나누면 배포가 부팅에 실패한다.

브랜치가 커지는 신호: 파일 수가 아니라 **설명 문장의 개수**로 본다. PR 본문에 "그리고"가 두 번 넘게 들어가면 나눌 후보다.

리뷰어도 같은 눈으로 본다 — diff 가 `CLAUDE_DIFF_LIMIT_BYTES` 를 넘어 잘리면 개별 지적 대신 **PR 을 쪼개 달라고** `CHANGES_REQUESTED` 한다.

## 대상 브랜치와 맞추기

브랜치가 오래되면 대상 브랜치와 벌어진다. 그때는 **대상 브랜치를 내 브랜치로 병합**한다.

```bash
git fetch origin
git merge origin/main        # 내 브랜치 위에서
```

**이미 원격에 올라간 브랜치를 rebase 로 갈아엎지 않는다.** 그 브랜치를 받아 간 사람과 리뷰어가 보던 이력이 사라지고, 리뷰 코멘트가 사라진 커밋을 가리키게 된다.

아직 아무 데도 올리지 않은 로컬 브랜치는 rebase 해도 된다 — 잃을 이력이 없다.

충돌이 나면 **양쪽을 다 읽고** 푼다. 어느 쪽이 맞는지 모르면 지우지 말고 물어본다.

이미 머지된 마이그레이션 파일은 충돌을 풀 때도 수정·삭제하지 않는다. 새 버전을 하나 더 만든다.

## 재작업은 같은 브랜치에서

리뷰에서 지적을 받으면 **같은 브랜치에 이어서 push** 한다. 새 브랜치를 파면 리뷰 이력이 끊기고 PR 이 하나 더 생긴다.

자동화도 같다 — 지적이 남으면 `fix` 노드가 같은 브랜치에서 돈다.

수정 커밋도 자기 몫의 메시지를 갖는다 — 지적 하나를 고쳤으면 그 사실이 커밋 제목에 보이게 쓴다.

여러 노드가 한 브랜치에 push 할 때는 push 가 밀린다. 그때는 `git pull --rebase` 후 다시 push 한다(병렬 노드가 같은 방식으로 동작한다).

## 머지 뒤 정리

- 머지는 `gh pr merge --squash --delete-branch` 다. 소스 브랜치가 함께 사라진다.

- 머지된 브랜치를 남겨 두지 않는다 — 목록에 남은 브랜치는 "아직 안 끝난 일"로 읽힌다.

- 로컬에서도 지운다: `git branch -d <이름>`. `-D` 는 병합되지 않은 브랜치를 지우므로, 정말 버릴 때만 쓴다.

- **머지되지 않은 브랜치는 지우기 전에 확인한다.** `git log --oneline main..<브랜치>` 로 잃을 커밋이 있는지 본다.

자동화의 청소 잡은 `claude/*` 중 **열린 PR 이 없고 기본 브랜치 대비 `ahead_by == 0`** 인 것만 지운다. 사람 브랜치는 이 규칙에 걸리지 않으므로 직접 지운다.

`main` 은 보호 브랜치다. 직접 push 하지 않고 PR 로만 들어간다.

### 검토를 넘길 때 남는 브랜치는 하나다

에이전트가 사람에게 검토를 요청하는 시점(= PR 을 여는 시점)에, **그 작업으로 생긴 브랜치는 하나만 남아 있어야 한다.**

작업 도중에 만든 브랜치 — 실험용, 되돌리려고 떠 둔 사본, 나눠 보려다 만 것 — 는 PR 을 열기 전에 지운다. 검토자가 보는 것은 **PR 하나와 그 소스 브랜치 하나**다.

브랜치가 여러 개 남아 있으면 검토자는 어느 것이 검토 대상인지, 나머지는 버려도 되는지 판단할 수 없다. 그 판단을 검토자에게 떠넘기지 않는다.

`split` 노드가 나눈 하위 작업도 예외가 아니다 — 하위 이슈마다 자기 PR 과 자기 브랜치 하나씩이고, 상위 작업이 쓰던 브랜치는 남기지 않는다.

## 적발 신호

| 신호 | 문제 |
|---|---|
| `feature-1`·`tmp`·사람 이름 브랜치 | 이름만 보고 내용을 알 수 없다 |
| 한 브랜치에 리팩터링 + 동작 변경 | 리뷰어가 필요한 변경을 가려낼 수 없다 |
| 엔티티 변경만 있고 마이그레이션이 다른 브랜치 | 배포가 부팅에 실패한다 |
| 사람이 만든 `claude/issue-N` | 자동화의 머지·청소 판별과 충돌한다 |
| 올라간 브랜치를 force push | 리뷰 코멘트가 사라진 커밋을 가리킨다 |
| 리뷰 지적마다 새 브랜치 | 이력이 끊기고 PR 이 늘어난다 |
| 머지됐는데 남아 있는 브랜치 | 끝난 일이 남은 일처럼 보인다 |
| 사람이 `claude/issue-N` 에 직접 push | 에이전트가 모르는 변경이 브랜치에 섞인다 |
| PR 을 넘겼는데 그 작업의 브랜치가 둘 이상 남아 있다 | 검토자가 무엇을 볼지 판단해야 한다 |

## 체크리스트

- [ ] 브랜치 이름이 `<type>/<주제-kebab>` 이고, 이름만 읽고 목적을 말할 수 있는가

- [ ] 이 브랜치의 목적을 한 문장으로 말할 수 있는가 (리팩터링과 동작 변경이 섞이지 않았는가)

- [ ] 대상 브랜치와 벌어졌으면 병합으로 맞췄는가 (올라간 이력을 갈아엎지 않았는가)

- [ ] 리뷰 지적을 같은 브랜치에 이어서 올렸는가

- [ ] 검토를 넘기는 시점에 이 작업의 브랜치가 하나만 남아 있는가

- [ ] 머지 뒤 원격·로컬 브랜치를 지웠는가
