# 업무 분해 판정

큰 업무를 받았을 때 **쪼갤지 말지를 먼저 정하고**, 쪼갠다면 축과 개수를 정한다. 실행은 `harness-graph` 가 한다.

**쪼개는 것은 비용이다.** 자식은 이 대화를 모르므로 배경을 다시 써 줘야 하고, 결과를 합치고 검증하는 일이 새로 생긴다.
그 비용보다 얻는 것이 클 때만 쪼갠다 — **ponytail** 의 사다리를 여기에도 적용한다.

## 사다리 — 성립하는 첫 단에서 멈춘다

1. **애초에 다 할 필요가 있는가?** 요청이 정말 그 범위를 요구하는지 먼저 본다. 아니면 줄이고 한 줄로 말한다.

2. **한 덩어리로 되는가?** 파일 몇 개를 순서대로 고치면 끝나는 일은 쪼개지 않는다. 여기서 멈추는 경우가 가장 많다.

3. **순차로 나누면 되는가?** 한 에이전트가 단계를 밟으면 되는 일에 여러 에이전트를 띄우지 않는다.
   `harness-loop` 로 충분한지 먼저 본다.

4. **그제서야 분해한다.** 아래 판정 기준 중 하나라도 걸릴 때만이다.

## 쪼개는 기준 — 셋 중 하나라도 걸릴 때

| 기준 | 무엇을 뜻하나 | 예 |
|---|---|---|
| **영역 독립** | 서로 다른 영역을 만지고 계약이 이미 확정됐다 | 백엔드 API 와 프론트 화면 |
| **컨텍스트 보호** | 중간 산출물이 대화를 가득 채운다 | 파일 200개 훑기, 로그 전수 분석 |
| **판단 독립** | 결론이 서로를 참조하지 않는다 | 계층별 코드 감사, 여러 후보 조사 |

**셋 다 아니면 쪼개지 않는다.** "일이 많아 보인다"는 기준이 아니다 — 많은 일을 순서대로 하는 것은 한 에이전트가 잘한다.

### 쪼개면 안 되는 것

- **계약이 아직 없는 일.** API 응답 형태가 안 정해졌는데 백엔드·프론트를 동시에 띄우면 둘이 서로 다른 것을 만든다.
  그래서 `api>web` 이 기본이고, `api+web` 은 `CONTRACT.md` 가 이미 있을 때만이다.

- **같은 파일을 고치는 일.** 두 자식이 한 파일을 고치면 나중에 온 쪽이 덮어쓴다. 격리해도 합칠 때 충돌이 난다.

- **엔티티 변경과 그 마이그레이션.** 한 커밋에 함께 들어가야 배포가 부팅한다 — 나누지 않는다.

- **앞 결과를 봐야 다음을 정하는 일.** 조사해 보고 방향을 정하는 작업은 순차다.

- **사용자에게 물어야 하는 일.** 자식은 질문할 수 없다. 결정이 필요하면 먼저 물어보고 쪼갠다.

## 축을 고른다 — 파일이 겹치지 않는 선

**쪼개는 선은 "일의 종류"가 아니라 "건드리는 파일"이다.** 종류가 달라도 같은 파일을 고치면 한 덩어리다.

이 저장소에서 실제로 겹치지 않는 선은 다음 셋이다.

- **영역** — `backend/` 와 `frontend/`. 계약(`CONTRACT.md`)이 확정된 뒤에만 병렬. 노드로는 `api` 와 `web` 이다.

- **계층** — 백엔드 안에서 리포지토리 / 구현 레이어 / 도메인 서비스 / 컨트롤러. 수직 슬라이스 하나를 여럿이 나눠 갖지 않는다.

- **도메인** — `user` / `order` / `payment`. 같은 계층이어도 도메인이 다르면 파일이 다르다. 백엔드는 도메인이 모듈 경계(`core/core-*`)라 특히 잘 갈린다.

읽기 전용 작업(조사·감사·측정)은 파일을 고치지 않으므로 **어떤 축으로 나눠도 안전하다.** 여기서는 개수만 관리한다.

## 개수 — 3~5개

한 번에 3~5개. 2개면 순차로 하는 게 낫고, 6개를 넘으면 합치고 검증하는 일이 본 작업보다 커진다.

상한을 넘을 만큼 조각이 많으면 **축이 잘못됐다.** 더 굵은 축으로 다시 나눈다.

이슈 자체를 쪼개야 할 만큼 크면 그건 분해가 아니라 `split` 노드의 일이다 — 하위 이슈로 나누고 각자 PR 을 갖게 한다.

## 자식에게 줄 것

자식은 이 대화를 하나도 모른다. 다음 넷을 매번 적는다 — 하나라도 빠지면 자식이 지어낸다.

1. **목표** — 무엇을 끝내면 완료인지. "잘 해줘"가 아니라 검사 가능한 문장으로.

2. **경계** — 고쳐도 되는 경로와 고치면 안 되는 경로. `core/core-order/` 만, 같은 식으로 적는다.

3. **배경** — 파일 경로, 에러 메시지, 이미 정해진 계약, 읽어야 할 스킬 경로. 공유 배경은 **자식마다 반복해서** 적는다.

4. **보고 형식** — 무엇을 돌려받을지. 결과를 합쳐야 하면 형식을 고정한다.

그리고 항상 덧붙인다: **커밋하지 말 것**, **요청 범위 밖을 고치지 말 것**.

## 자식 보고는 사실이 아니다

**자식이 "완료했다"고 하면 그것은 자기 보고이지 검증이 아니다.** 특히 외부에 영향을 주는 일
(파일 생성, 빌드, 업로드)은 반드시 내가 직접 확인한다.

- 파일을 만들었다면 그 경로를 열어 본다.

- 검사가 통과했다면 그 명령을 다시 돌려 본다. **`BUILD SUCCESSFUL` 은 증명이 아니다** — 테스트 결과 XML 의 실계수를 본다.

- 숫자를 보고했다면 표본 하나를 다시 세어 본다.

합치기 전에 확인하고, 어긋나면 그 자식만 다시 돌린다.

## 순서 — 판정부터 보고까지

1. **사다리를 탄다.** 2~3단에서 멈추면 여기서 끝이다. 쪼개지 않는다고 한 줄로 말한다.

2. **축과 개수를 정한다.** 파일이 겹치지 않는지 확인한다. 겹치면 그 둘은 한 조각이다.

3. **그래프 문자열로 적는다.** `harness-graph` 가 실행할 수 있는 형태다.

   ```text
   api>web>e2e      계약을 먼저 확정하고 화면, 마지막에 검증
   api+web>test     계약이 이미 있으면 병렬, 검증은 합친 뒤
   plan>code?fix    계획 먼저, 구현 실패 시에만 수습
   ```

4. **실행은 `harness-graph` 에 넘긴다.** 문법 해석도 그쪽이 한다 — 여기서 직접 파싱하지 않는다.

5. **합치고 검증한다.** 위 "자식 보고는 사실이 아니다" 대로 확인한 뒤 사용자에게 보고한다.

## 하지 않는다

- 그래프 문법을 직접 해석하지 않는다 — `harness-graph` 가 `.github/agent/graph.js` 에 맡긴다.

- 자식에게 또 자식을 띄우게 하지 않는다. 분해는 한 겹이다.

- 쪼갤 수 있다는 이유로 쪼개지 않는다. 사다리 2단에서 멈추는 것이 가장 흔한 정답이다.

- 커밋하지 않는다. 변경은 작업 트리에 남기고 사람이 확인해 커밋한다.
