# 책임주도 설계 — 규칙 요약

> 개념의 배경과 단계별 코드 예제(영화 예매 도메인)는 같은 폴더의 [reference.md](reference.md) 에 있다. 설계 근거를 설명하거나, 리팩터링 단계를 계획하거나, 사람에게 개념을 가르칠 때만 reference.md 를 읽는다.

> 코드 작성·리뷰 판단에는 이 문서만으로 충분하다.

## 전제 — 코드는 누구나 읽기 쉬워야 한다

- 처음 보는 사람도 읽고 바로 이해할 수 있어야 한다. 화려한 문법보다 단순하고 평범하게 쓴 코드가 정답이다.

- 짧은 코드 ≠ 단순한 코드. 판단과 반복은 코드가 길어지더라도 `if`/`for` 로 풀어서 쓴다. `firstOrNull { }`·`any { }`·`fold` 같은 람다·함수형 체이닝은 최소화한다.

  람다가 필요해 보이는 자리도 이름 있는 클래스로 만들어 의도를 드러낸다.

- 설계 기법(추상화·다형성·패턴)은 코드를 고치기 쉽게 만들 때만 가치가 있다. 바뀔 일이 없는 곳에 미리 구조를 만들지 않는다.

## 핵심 원칙 8가지

핵심 질문: **"이 로직을 가장 잘 아는 클래스는 누구인가?"**

1. **책임의 이동** — 다른 클래스의 값을 꺼내 판단하는 로직은, 그 값을 가진 클래스 안으로 옮긴다. 값을 노출만 하고 판단을 바깥에 맡기는 것은 "바보 데이터 객체"다.

   getter 로 모든 필드를 여는 것은 내부를 통째로 공개한 것과 같다(추측에 의한 설계).

2. **캡슐화 경계** — 의존하는 클래스 수를 줄이려면 도메인의 관계를 코드 구조로 옮긴다. (정책 1 : N 조건 → 정책이 조건을 소유하고 바깥에서 가린다.)

3. **다형성** — 목적이 같고 방법만 다른 로직들은 종류별 클래스로 나누고, 같은 메시지(메서드 시그니처) 하나로 통일한다. 타입 검사 조건문(`when`/`if` 분기)이 여러 곳에 반복되면 전환 신호다.

4. **역할 구현 수단 선택** — 아래 표 참고. 기준은 "같이 쓰는 코드가 있는가" 하나다.

5. **제어 분산** — 서비스는 흐름과 트랜잭션 경계만 갖는다. 판단·계산이 서비스에 있으면 중앙집중식 제어다. 애매하면 요구사항을 문장으로 써서 **목적어를 주어로** 바꾼다: "상영을 예매한다" → `screening.reserve(...)`.

6. **예외 케이스도 협력에 참여** — "없음"을 `null` + null 분기로 처리하지 않고 같은 역할을 하는 클래스(`NoneDiscountPolicy` 방식)로 만든다. 협력 상대의 개수가 변하면 여러 객체를 묶어 같은 자리에 세운다(컴포지트).

7. **상속은 역할 대체용** — 상속은 코드 물려받기가 아니라 역할 대체가 목적이다.

   상속 설계도 대개 충분하니 **아래 둘 중 하나에 걸릴 때만** 합성(별도 클래스로 분리해 필드로 참조)으로 옮긴다: ① 자식이 부모의 `protected` 필드·내부 구현에 손을 댄다 ② 실행 중에 종류를 바꿔야 한다. 둘 다 아니면 그대로 둔다.

8. **부탁과 실행을 떼어 놓는다** — 부탁(메서드 시그니처)은 부르는 쪽이, 실행은 받는 쪽이 정한다. 그래서 부탁은 협력 상대를 **꽂는 자리**가 된다.

   협력 객체를 안에서 직접 만들면 종류가 컴파일 시점에 굳어 다형성이 무의미해지므로, **생성자로 주입 받는다** (`@Autowired` 필드 주입 금지가 이 이유다).

## 인터페이스 vs 추상 클래스 vs 구체 클래스

| 상황 | 선택 |
|---|---|
| 그 역할을 맡을 클래스가 하나뿐 | 그냥 클래스 (미리 나누지 않는다) |
| 여러 클래스가 공통 흐름·필드를 같이 쓴다 | 추상 클래스 — 공통 흐름은 부모의 일반 메서드, 다른 부분만 `protected abstract` |
| 같이 쓰는 코드 없이 메서드 약속만 필요 | 인터페이스 |

클래스를 나눌지 판단하는 세 기준 (하나라도 걸리면 나눌 신호): ① 바뀌는 이유가 다른 코드 ② 함께 사용되지 않는 메서드·필드 ③ 함께 초기화되지 않는 필드 (일부 필드를 비워둬야 생성된다면 확실한 신호).

## 무엇을 감추고 있나

`public` 인지 아닌지는 기준이 아니다.

판정 기준은 하나다: **내부 구현을 바꿨을 때 공개된 시그니처가 따라 바뀌면, 그건 인터페이스가 아니라 구현이다.** 필드 타입을 바꾸면 같이 바뀌는 `getPercent(): Double` 은 구현이고, 내부를 무엇으로 바꿔도 그대로인 `calculateDiscount(screening): Money` 는 인터페이스다.

그래서 모든 필드에 getter 를 연 클래스는 클래스 전체가 구현이다.

| 감추는 것 | 이름 | 수단 |
|---|---|---|
| 필드의 이름·타입·구조 | 데이터 캡슐화 | 부탁을 먼저 정하고 필드는 마지막에 |
| 협력 상대의 **종류** | **타입 캡슐화** | 역할(추상 클래스·인터페이스) + 생성자 주입 |
| 협력 상대의 **개수** | — | 여러 개를 묶은 클래스를 같은 자리에 (컴포지트) |

타입 캡슐화를 떠받치는 것이 DIP(양쪽 모두 역할에 기댄다) · LSP(자식이 부모 자리를 대신할 수 있다) · OCP(그 결과 새 종류는 클래스 추가만으로 들어온다)다.

## 일을 맡길 클래스 고르는 순서 (GRASP)

1. 기능을 "맡길 일"로 바꾼다. ("상영을 예매한다" → 예매를 만들어낼 일)

2. 그 일에 필요한 정보에 가장 잘 **답하는** 클래스를 찾는다. 필드로 갖고 있을 필요는 없다 — 계산하든 남에게 묻든 답할 수 있으면 된다.

3. 후보가 여럿이면 **새 연결(의존)이 안 생기는 쪽**을 고른다.

4. 상관없는 일이 한 클래스에 모이면 나눈다.

5. 자기가 못 하는 부분은 다른 클래스에 부탁으로 넘긴다 — 그 부탁이 상대의 새 일이 된다.

6. 필드는 마지막에, 행동을 구현하다 필요해진 것만 넣는다.

| GRASP 패턴 | 쉬운 말로 |
|---|---|
| Information Expert (정보 전문가) | 그 질문에 가장 잘 답하는 클래스에게 맡긴다 |
| Creator (창조자) | 만들어질 객체를 품거나, 만들 재료를 가진 클래스가 만든다 |
| Low Coupling (낮은 결합도) | 새 연결이 안 생기는 배치를 고른다 |
| High Cohesion (높은 응집도) | 상관없는 일이 모이면 클래스를 나눈다 |
| Polymorphism (다형성) | 종류 확인 조건문 대신, 종류별 클래스 + 같은 부탁 |
| Protected Variations (변경 보호) | 자주 바뀌는 것들 앞에 잘 안 바뀌는 창구를 세운다 |

**이름은 업무(도메인) 용어에서 가져온다.** 업무에서 "할인 정책"이라 부르면 코드에도 `DiscountPolicy` 가 있어야 한다. 코드가 업무를 닮을수록 수정 위치가 이름으로 예측된다.

`Manager`·`Processor`·`Util` 같은 이름은 금지 신호다.

**설계 검증법**: 요구사항을 하나 추가해 보고 기존 코드를 몇 곳 고치는지 센다. 새 종류 추가가 클래스 추가만으로 끝나면(기존 수정 0곳) 좋은 설계다.

## 이 프로젝트에 적용하면

- 엔티티의 행위 메서드가 곧 "책임의 이동"이다 (kotlin-entity). 서비스가 엔티티 값을 꺼내 비교·대입하면 위반이다.

- 도메인 서비스는 흐름과 트랜잭션만 조립한다 (kotlin-domain-service).

- 구현 레이어를 Finder·Appender 로 나누는 것이 곧 "상관없는 일 분리"다 (kotlin-implement).

- 정책·계산 종류가 늘어 `when` 이 자라기 시작하면 다형성 구조로 전환한다. 단, 종류가 하나뿐일 때 미리 인터페이스를 만들지 않는다 (kotlin-common 2대 원칙).

## 적발 신호

**Critical — 머지 차단 사유**

| 신호 | 무엇이 문제인가 |
|---|---|
| 객체의 종류를 확인해서 다른 코드가 할 일을 대신 결정 (`if (x.type == PERIOD)…`) | 절차적 코드의 핵심 증상 |
| 서비스가 객체의 값을 꺼내 판단·계산한 뒤 다시 대입 | 로직이 데이터 밖에 있음 |
| getter/setter 로 모든 필드를 열어두고 바깥에서 조립 | 내부가 통째로 노출, 변경이 번짐 |
| 내부 구현을 바꾸면 공개 메서드 시그니처가 따라 바뀜 | 인터페이스인 척하는 구현, 변경이 번짐 |
| 협력 객체를 클래스 안에서 직접 생성 (생성자로 주입받지 않음) | 종류가 컴파일 시점에 굳어 다형성이 무의미 |

**Important — 참고 코멘트**

| 신호 | 무엇이 문제인가 |
|---|---|
| 종류별 `when` 분기가 여러 곳에 반복 | 새 종류마다 기존 코드 수정 강제 |
| "없음"을 `null` + null 확인으로 처리 ("없음" 클래스를 만드는 대신) | 분기 증식, 의미가 모호해짐 |
| 한 클래스에 생성·계산·판단 등 상관없는 일이 혼재 | 고칠 곳 찾기 어려움, 버그 위험 |
| 같이 쓰는 코드가 없는데 추상 클래스로 상속 | 불필요한 묶임 |
| 자식이 부모의 `protected` 필드·내부 구현에 기댐 | 상속 남용, 합성으로 바꿀 신호 |
| 종류가 하나뿐인데 미리 만든 인터페이스·확장 지점 | 쓰지 않는 구조, 추측에 의한 설계 |
| 문제 없는 상속을 합성으로 미리 전환 | 바뀔 일 없는 곳에 만든 구조 |
| 업무 용어와 무관한 이름 (`Manager`, `Processor`, `Util`) | 수정 위치를 이름으로 예측 불가 |

## 체크리스트

- [ ] 처음 보는 사람이 바로 읽고 이해할 수 있는가 — 압축 문법 없이 단순하게 썼는가

- [ ] 판단·계산이 그 정보를 가진 클래스 안에 있는가

- [ ] 바깥 코드가 데이터 구조가 아니라 행동(메서드)에 기대는가

- [ ] 종류 확인 조건문이 종류별 클래스 + 같은 부탁으로 바뀌었는가

- [ ] 공통 창구 수단이 맞는가 — 같이 쓰는 코드 있으면 추상 클래스, 약속만이면 인터페이스, 하나뿐이면 그냥 클래스

- [ ] "없음" 같은 예외 상황도 같은 협력에 참여하는가 (null 분기 없음)

- [ ] 협력 객체를 안에서 만들지 않고 생성자로 주입받는가

- [ ] 내부 구현을 바꿔도 공개 시그니처가 그대로인가

- [ ] 새 종류 추가가 클래스 추가만으로 끝나는가 (기존 코드 수정 0곳)

- [ ] 클래스·메서드 이름이 업무 용어와 일치하는가
