# 제작 그래프

`$ARGUMENTS` 의 첫 낱말이 그래프 문자열이고 나머지가 작업 지시다.

그래프 문자열이 아직 없다면 — 쪼갤지 말지, 어떤 축으로 몇 개로 나눌지는 **harness-split** 이 정한다.

## 문법을 직접 해석하지 않는다

`.github/agent/graph.js` 에게 펼치게 한다 — 해석기가 둘이면 CI 와 로컬의 문법이 갈라진다.

```bash
CLAUDE_GRAPH="<그래프>" node .github/agent/graph.js
```

나온 `stages` 가 실행 목록이다. **단계 배열의 JSON** 이고, 각 단계는 그 단계에서 나란히 돌 노드들이다.

항목 하나는 `{ node, label, rescue, make_pr }` 다 — `node` 가 무엇을 돌릴지, `rescue` 가 실패했을 때 이어받을 노드다.

이름 규칙·중복·예약어 검사도 `graph.js` 가 한다. `.github/agent/nodes/<이름>.md` 가 없으면 경고를 낸다.

## 노드 하나 = 서브에이전트 하나

| 무엇 | 어디서 |
|---|---|
| 지시문 | `.github/agent/nodes/<이름>.md` — 노드당 파일 하나 |
| 도구·add-dir | 같은 파일의 frontmatter (`tools`·`add-dir`·`allowed-tools`) |

지시문을 먼저 주고 작업 지시를 뒤에 붙인다. 마지막에 **커밋하지 말라**고 명시한다 — CI 는 커밋하지만 여기서는 작업 트리에 남기고 사람이 커밋한다.

`add-dir` 가 그 노드가 볼 수 있는 영역을 정한다 — `api` 는 `backend`, `web` 은 `frontend`, `code` 는 둘 다다. 그 밖을 고치라고 시키지 않는다.

노드 보고는 `.claude/state/graph/<이름>/<노드>.md` 에 남긴다.

## 순서 — 단계대로

시작 기준점과 기존 변경을 기록해 리뷰 루프로 넘긴다.

같은 단계의 노드(`+` 병렬)는 **서로 기다리지 않아도 되는 사이**다. API 계약이 필요한 `web` 은 계약 확정 후 실행한다. 둘 중 하나를 고른다.

- **계약이 확정되고 서로 다른 영역을 만지면** 동시에 띄울 수 있다. 실행기가 worktree 격리를 지원하면 각 노드의 기준점과 수정 patch(신규 파일 포함)를 남긴다. 주 대화가 패치를 작업 트리에 순서대로 적용·충돌 해결·검증한 뒤 다음 단계로 넘긴다.

- **영역이 겹치거나 격리를 쓸 수 없으면** 차례로 돌린다. 순서 제약이 없다는 뜻이지 반드시 동시라는 뜻이 아니다.

다음 단계는 앞 단계가 전부 끝난 뒤 시작한다.

**단계 수에는 상한이 없다.** 대신 노드가 통틀어 몇 번 도는지에 상한이 있다 — `CLAUDE_MAX_STEPS`(기본 12)다.

## 바통

같은 작업 트리의 순차 노드는 앞 노드가 고친 파일을 읽는다. 격리한 노드의 파일은 통합을 완료한 뒤 읽는다. 통합되지 않은 별도 worktree 의 산출물이 자동으로 보인다고 가정하지 않는다.

코드만으로 부족한 것은 노드 지시문이 문서로 남기게 되어 있다 — `plan` 은 `PLAN.md`, `api` 는 `CONTRACT.md`. 그 문서를 읽으라고 다음 노드에게 알린다.

스펙이 있으면 `specs/<기능>/plan.md` 가 루트 `PLAN.md` 보다 앞선다. 어느 쪽이 기준인지 다음 노드에게 명시한다.

## 수습 (`?`)

`rescue` 가 있는 노드는 **그 대상이 실패했을 때만** 이어받는다. 성공했으면 건너뛰고 건너뛴 사실을 알린다.

수습 노드에게는 무엇이 실패했는지와 그 노드의 마지막 보고를 함께 준다. 어중간하게 남은 변경을 정리하고 이어받으라고 지시한다.

**수습받지 못한 실패가 하나라도 남으면 제작 실패다.** 리뷰로 넘어가지 않고 멈춘다.

## 제작이 끝나면 — 리뷰 한 번

`harness-loop` 절차를 따르되 **구현이 아니라 리뷰부터** 시작한다. 그래프가 이미 만들었기 때문이다. 시작 기준점·변경 파일·검사 원출력도 함께 전달한다.

검사 원출력에는 **테스트 실계수**를 포함한다. `BUILD SUCCESSFUL` 만 넘기면 리뷰어가 검증 여부를 판단할 수 없다.

리뷰어에게 이 변경이 그래프로 만들어졌다고 알린다 — `PLAN.md`·`CONTRACT.md` 처럼 노드가 남기는 인수인계 문서를 범위 밖 변경으로 오해하지 않게.

지적을 고칠 담당자는 박아 두지 않는다. 그 변경이 건드린 영역이 정한다 — 백엔드만이면 `api`, 프론트만이면 `web`, 양쪽이면 `code`·`fix` 다.

## 끝나면

`.claude/state/graph/<이름>/state.json` 에 그래프·작업·상태와 노드별 기록(단계·노드·수습 대상·성공 여부), 그리고 리뷰 라운드를 남긴다.

## 하지 않는다

- 그래프 문법을 직접 파싱하지 않는다 — `.github/agent/graph.js` 가 예약어·이름 규칙·중복 이름까지 검사한다.

- 노드 지시문을 이 문서에 옮겨 적지 않는다 — 원본은 `.github/agent/nodes/<이름>.md` 이고 사람이 거기서 고친다.

- 노드에게 또 노드를 띄우게 하지 않는다. 분해는 한 겹이다.

- 커밋하지 않는다.
