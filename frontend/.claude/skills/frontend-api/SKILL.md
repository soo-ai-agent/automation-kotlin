# api / types — 엔드포인트와 서버 계약의 사본

## api — 엔드포인트 1:1

경로 상수 + 요청 함수. **그 이상 아무것도 하지 않는다.** 동봉 정답: `frontend/src/user/api/user.ts`.

```ts
const USERS = "/api/v1/users";

export const user = {
    list(): Promise<ApiResult<User[]>> {
        return apiClient.get<User[]>({path: USERS});
    },

    delete(id: number): Promise<ApiResult<void>> {
        return apiClient.delete<void>({path: `${USERS}/${id}`});
    },
};
```

- 도메인당 파일 1개, `export const <도메인> = {...}` 객체 네임스페이스. 호출부는 `user.list()` 로 읽힌다.

- 경로는 파일 상단 상수로 한 번만 쓴다. 함수마다 문자열을 반복하지 않는다.

- 요청 함수에 **반환 타입을 명시**한다. 추론에 맡기면 `undefined` 가 섞여 들어온다.

- 여기서 금지: 상태코드 분기, 사용자 메시지, `notify`, 리다이렉트, 업무 계산 — 전부 `services` 의 몫이다.

## 서버 DTO 는 `types/` 에만 산다

서비스 파일 안에 응답 인터페이스를 선언하면, **계약서(서버 응답)와 업무 규칙이 한 파일에서 섞인다.** 서버가 필드를 바꿀 때 어디를 보면 되는지가 흐려진다.

| 무엇 | 어디 |
|---|---|
| 요청 본문·응답 페이로드·행(row) | `<도메인>/types/<자원>.ts` |
| 클라이언트 옵션 — `*Options`·`*Query`(주입점·페이지) | 서비스 파일 |
| 결과 표현 — `*Outcome`(결과 enum·판정) | `<도메인>/enums/` |

**`types/` 는 아무것도 import 하지 않는 바닥이다.** `types/` 가 `services/` 를 참조하면 방향이 뒤집힌 것이다 — 값(함수·상수)이 필요해 보이면 그건 DTO 가 아니다.

## 타입 규칙

- `any` 금지. `unknown` 도 최소화 — 모양을 정말 보장할 수 없는 자리(catch 예외, 직렬화 경계)에서만 쓰고,
  "왜 모를 수밖에 없는지" 주석을 달아 경계에서 즉시 좁힌다. 동봉 `apiClient.ts` 의 `body: unknown` 주석이 표준 예다.

- **지역 변수에도 타입을 적는다** (rules.md MUST "타입 명시"): `const res: ApiResult<void> = await user.delete(id);`

- `object`·`{}`·`Record<string, unknown>` 을 도메인 데이터에 쓰지 않는다. 필드를 아는 데이터는 필드를 적는다.

- `props` 는 항상 명시적 `type`/`interface`. 훅 파라미터가 2개를 넘으면 이름 있는 객체(`UseXxxParams`)로 받는다.

- 닫힌 값 집합은 `enum`(선언은 `enums/` 에 — `frontend-common`). 객체 구조·함수 시그니처는 enum 대상이 아니다.

- **DTO 는 서버 필드명을 그대로 쓴다.** camelCase 로 내려오는 그대로 — 개명하면 계약서(`CONTRACT.md`)와 눈으로 대조할 수 없다(`api-contract` 미러링).
  화면용 이름이 필요하면 `services` 에서 화면 모델로 변환한다.

## nullable — `?` 와 `| null` 은 서버 코드를 열어 정한다

프론트 DTO 는 서버 계약의 사본이다. **추측으로 `?` 를 붙이면 그 순간 계약이 두 개가 된다** — 서버는 늘 보내는데 화면은 "안 올 수도 있다"고 분기한다.

**`?` 는 "필드 자체가 안 올 수 있다", `| null` 은 "필드는 오지만 값이 빌 수 있다"는 뜻이다.** 계약이 다르면 타입도 다르다.

| 서버가 이렇게 주면 | 프론트는 이렇게 |
|---|---|
| non-null 필드 | **필수**. `?` 도 `\| null` 도 붙이지 않는다 |
| nullable 인데 키는 늘 보냄(직렬화 옵션 없음) | `\| null` 만 |
| nullable 이고 null 이면 키를 생략(`@JsonInclude(NON_NULL)`) | `?` 만 |
| 하위호환으로 정말 없을 수 있는 신규 필드 | `?` + "언제부터 생긴 필드인지" 주석 |

읽는 법(Kotlin/Spring): 필드 타입 끝의 `?` 가 nullable 여부다. 클래스 위 `@JsonInclude(NON_NULL)` 이 있으면 null 필드는 키 자체가 빠진다 → `?`.
없으면 nullable 이어도 `"field": null` 로 온다 → `| null`.

- **`x?: T | null` 은 두 없음이 정말 다른 뜻일 때만** 쓴다 — "안 넘김"과 "null" 이 서로 다른 일을 시키는가. 같은 뜻이면 하나로 모은다.

- **"누락 시 0" 류 주석은 위험 신호다.** 십중팔구 추측으로 붙인 `?` 다 — 서버를 열어 확인하고 필수로 바꾼다.

- **매퍼가 값을 보장하면 타입도 보장해야 한다.** 매퍼가 항상 숫자를 만드는데 타입이 `?: number` 면, 화면은 오지 않을 `undefined` 를 평생 분기한다.
  바로잡으면 테스트 픽스처가 먼저 깨진다 — 픽스처를 실 응답에 맞춘다. 타입을 되돌리지 않는다.

### `?` 를 쓸 거면 왜 없을 수 있는지 적는다

`?` 만 봐서는 "안 올 수 있는 값"인지 "안 줘도 되는 값"인지 구분할 수 없다. **선언마다 그 자리에** 사유를 한 줄로 남긴다 — 묶음 위 한 줄은 위반이다(rules.md MUST).
문장은 `<언제> 없음` 꼴로 끝낸다. **사유를 못 적겠으면 `?` 를 지우라는 뜻이다** — 기본값·빈 배열·전용 타입으로 바꾼다.

쓸 만한 이유는 네 갈래뿐이다: 외부 규격 · 원천 데이터 누락 · 주입점/기본값 · 화면마다 다른 선택 입력. 이 넷에 안 들어가면 대개 습관적 `?` 다.

```ts
// O — 필드마다 언제 없는지가 다르고, 그 차이가 그 자리에 적혀 있다
export interface MapMarker extends LatLng {
    type: MapMarkerType;
    purpose?: string;     // 설치목적을 주는 원천이 CCTV 뿐이라 그 밖의 마커에는 없음
    phone?: string;       // 전화로 도움을 청할 수 있는 시설이 아니면 없음
}
```

같은 문장이 여러 줄 반복되면 주석을 줄일 게 아니라 **`?` 를 줄일 자리다** — 함께 비는 값이면 전용 타입 한 덩이로 묶어 그 덩이 하나를 `?` 로 만든다.
예외는 와이어 DTO 하나 — 서버가 평평하게 보내는 응답은 묶으면 모양이 거짓이 된다. 이때만 타입 위에 한 번 적되, 서버 코드 어디를 봤는지 근거를 함께 적는다.

### 이름을 되풀이하는 주석은 지운다

기본은 무주석이다. 주석은 **코드가 말할 수 없는 것**만 적는다 — 왜 없을 수 있는지, 외부 규격, 단위·범위, 의도한 규칙 이탈.

```ts
// X — 지운다. 이름과 타입이 이미 말한다
/** 소요 ms. */  durationMs: number;

// O — 남긴다. 코드가 말할 수 없는 것이다
/** 0~1. */      successRate: number;
```

이름만 되풀이하는데 그 줄에 `?` 가 있으면, 지우지 말고 **`?` 사유로 바꿔 쓴다.**

## 엔드포인트도 대조한다

프론트가 부르는 경로가 서버에 없으면 그 화면은 영원히 404 다. 타입만 맞추지 말고 **경로도 맞춘다.**

```
서버:  컨트롤러의 @RequestMapping + @GetMapping/@PostMapping 을 모아 목록으로
프론트: api/ 의 경로 상수를 모아 목록으로            →  차집합이 0 이어야 한다
```

없는 경로를 부르는 화면을 발견하면 **조용히 폴백을 넣지 말고** 보고한다 — 화면을 지울지 서버를 만들지는 사람이 정한다.
필드 목록의 대조 절차는 `api-contract` 가 담당한다.

## 적발 신호

| 신호 | 문제 | 심각도 |
|---|---|---|
| 서버 코드를 안 보고 붙인 DTO `?` ("누락 시 0" 주석) | 계약이 둘로 쪼개진다 | Critical |
| 서버에 없는 엔드포인트를 부르는 화면 | 영원히 404 | Critical |
| 사유 주석 없는 `?` 선언 | 안 오는 값인지 안 줘도 되는 값인지 못 읽는다 | Critical |
| DTO 필드를 서버 응답과 다른 이름으로 개명 | `CONTRACT.md` 와 눈 대조 불가 | Critical |
| `any`, 습관적 `?`, `Record<string, unknown>`, 사유 없는 `unknown` | 자료형 뭉개기 | Critical |
| api 계층의 상태코드 분기·사용자 메시지 | services 책임 침범 | Critical |
| 서버 DTO 가 서비스 파일 안에 선언됨 | DTO 의 거처는 `types/` | Important |
| api 함수 반환 타입 미선언 | `undefined` 가 추론에 섞여 들어온다 | Important |
| 이름을 되풀이할 뿐인 주석 | 정보 0, 이름 바뀌면 거짓말 | Important |
| 매퍼가 보장하는 값의 `?:` 타입 | 화면이 평생 헛분기 | Important |

## 체크리스트

- [ ] 서버 DTO 가 서비스가 아니라 `types/` 에 있고, 필드명이 서버 그대로인가

- [ ] DTO 의 `?`·`| null` 을 서버 응답 타입을 열어 정했는가(`@JsonInclude` 여부까지)

- [ ] `?` 마다 사유가 그 필드 자리에 있는가

- [ ] api 함수에 반환 타입이 있고 상태코드 분기가 없는가

- [ ] 부르는 엔드포인트가 서버 매핑에 전부 있는가
