# automation-kotlin Constitution

## Core Principles

### I. 규칙의 단일 출처는 스킬이다 (헌법은 사본이 아니라 포인터)

이 문서에 규칙을 복사해 적지 않는다. 규칙 본문은 아래가 갖는다.

- 공통 코딩 규칙 — `.claude/skills/`
- 백엔드 규칙 — `backend/.claude/skills/` (`kotlin-*` 16종)
- 프론트엔드 규칙 — `frontend/.claude/skills/`
- 머지를 막는 기준 — `common/docs/code-review/rules.md`
- 작업 규칙 진입점 — `CLAUDE.md`(Claude), `AGENTS.md`(Codex)

**근거:** 같은 규칙을 말하는 문서가 둘이면 에이전트는 둘 중 하나를 따르고, 어느 쪽인지 예측할 수 없다. 실제로 스킬만 고치고 주변 문서를 두었을 때 같은 과제에서 두 번 연속 옛 구조가 나왔다.

헌법과 스킬이 어긋나면 **스킬이 이긴다.** 헌법을 고쳐 맞춘다.

### II. 산출물은 한국어로 작성한다

`spec.md`·`plan.md`·`tasks.md`·체크리스트를 한국어로 쓴다. 사람이 검토하는 문서이기 때문이다.

다만 아래는 영어로 남긴다 — 명령이 이 문자열을 그대로 찾아 읽고 채우므로, 번역하면 단계 사이 연결이 조용히 끊긴다.

- 아직 정해지지 않은 자리 — `[NEEDS CLARIFICATION]`

- 번호 — `FR-001`·`SC-001`·`CHK001`·`T001`·`US1`·`P1`/`P2`/`P3`

- 병렬 가능 표시 — `[P]`

- 시나리오 낱말 — `**Given**`·`**When**`·`**Then**`

- 치환 토큰 — `__SPECKIT_COMMAND_*__`

절 제목은 `## Requirements (요구사항)` 처럼 병기한다. 상세는 `common/speckit-ko/README.md`.

### III. 새 동작에는 테스트가 같은 변경에 들어간다 (NON-NEGOTIABLE)

분기·정책·검증·상태 변경을 만들면 유닛 테스트를 **같은 변경에** 포함한다. "나중에 추가"는 없고, 테스트가 없는 새 동작은 미완성이다.

테스트 메서드 하나는 기능 하나만 검증한다. 통과시키려고 단언을 약화하거나 테스트를 지우지 않는다.

**`BUILD SUCCESSFUL` 은 증명이 아니다.** Gradle 은 캐시로 태스크를 건너뛰고도 성공이라 말하므로, 테스트 실계수를 세어 보고한다.

상세는 `backend/.claude/skills/kotlin-test`.

### IV. 레이어는 한 방향으로만 흐른다

상위에서 하위로만 참조한다. 건너뛰기와 역참조를 하지 않는다.

- 백엔드 — controller → domain service → implement → repository
- 프론트엔드 — screens → hooks → services → api → lib (Expo/RN 이라 화면 폴더가 `screens/` 다)

**엔티티는 구현 레이어 위로 올라가지 않는다.** 구현 레이어가 지역변수로 다루고 도메인 모델로 바꿔 올리는 것까지가 허용이다.

외부 시스템과 통신하는 코드는 예외 없이 `clients/client-*` 에 둔다. 엔티티나 컬럼을 바꾸면 같은 변경에 Flyway 마이그레이션이 들어간다.

상세는 `backend/.claude/skills/kotlin-module-layout`.

### V. 요청받은 것만 최소한으로 고친다

손대는 파일과 줄은 요청을 만족시키는 데 필요한 만큼으로 제한한다. 지나가다 눈에 띈 코드는 그대로 둔다.

요청받지 않은 리팩터링·개선·이름 변경을 곁들이지 않는다. 고쳐야 할 것 같으면 직접 고치는 대신 PR 본문에 적어 사람이 판단하게 한다.

리팩터링과 동작 변경을 같은 커밋에 섞지 않는다. 이 원칙을 어긴 변경은 **내용이 옳더라도** 되돌린다.

### VI. 규칙을 고치면 그 규칙을 말하는 문서를 전부 고친다

스킬 하나만 고치면 규칙은 바뀌지 않는다. 절차는 셋이다.

1. 바꾼 규칙의 **낱말**로 저장소 전체 md 를 훑는다. 옛 이름(모듈명·경로·타입명)도 검색어에 넣는다.
2. 걸린 문서를 규칙을 말하는 것과 예시로 언급만 하는 것으로 나눈다. 앞의 것은 반드시 고치고, 뒤의 것도 옛 이름이면 고친다.
3. 고친 뒤 같은 낱말로 다시 훑어 **0건**임을 확인한다. 일부러 남긴 것이 있으면 왜 남겼는지 그 자리에 적는다.

## 스펙과 코드가 어긋날 때

**스펙이 기준이다.** 구현 결과가 스펙과 다르면 코드를 고쳐 맞춘다.

스펙을 고쳐 코드에 맞추지 않는다. 그렇게 하면 기준이 사라지고, 다음 사람이 어느 쪽을 믿어야 할지 알 수 없게 된다.

스펙 자체가 틀렸다고 판단되면 조용히 고치지 말고 보고한다. 스펙을 바꾸는 것은 합의를 바꾸는 일이다.

에이전트가 구현할 때는 `specs/<기능>/` 의 `spec.md`·`plan.md`·`tasks.md` 를 먼저 읽는다.

## 시작 전 승인이 필요한 작업

되돌릴 수 없는 것들이라 **하기 전에** 사람에게 보고하고 승인을 받는다.

- **외부 API 를 30건 이상 호출하는 작업** — 대상·예상 호출 수·쿼터 영향 셋을 보고한다. 실검증도 예외가 아니며, 승인 전에는 1건으로만 확인한다.

- public API·DB 필드·외부에서 쓰는 함수의 **이름과 의미를 바꾸는 것**.

상세는 `CLAUDE.md` 와 `backend/.claude/skills/kotlin-client`.

## Governance

이 헌법은 스펙 주도 개발(`/speckit-*`)의 판정 기준이다. 코드 리뷰의 머지 차단 기준은 `common/docs/code-review/rules.md` 가 갖는다 — 둘이 어긋나면 그쪽이 이긴다.

**개정 절차.** 원칙을 더하거나 빼거나 뜻을 바꾸려면 (1) 무엇이 왜 바뀌는지 PR 본문에 적고, (2) 원칙 VI 의 전수 검색 절차를 밟아 같은 규칙을 말하는 다른 문서를 함께 고치고, (3) 아래 버전을 올린다.

**버전 규칙(유의적 버전).** MAJOR 는 원칙을 없애거나 뜻을 뒤집을 때, MINOR 는 원칙이나 절을 더하거나 지침을 크게 넓힐 때, PATCH 는 표현을 다듬거나 오타를 고칠 때 올린다.

**준수 확인.** 모든 PR 은 위 원칙을 지켰는지 확인받는다. 원칙을 어겨야만 하는 사정이 있으면 `plan.md` 의 Complexity Tracking 에 어긴 항목·필요한 이유·더 단순한 방법을 버린 이유를 적는다. 적지 않은 위반은 되돌린다.
