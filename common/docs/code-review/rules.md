# 코드 리뷰 규칙

> **이 문서는 에이전트가 읽습니다.** 팀 규칙을 여기에 추가하면 리뷰에 반영됩니다.

MUST 위반은 CHANGES_REQUESTED 사유가 되고, SHOULD 위반은 참고 코멘트만 남습니다.

스택별 상세 규칙은 영역 스킬이 담당합니다 — 백엔드 `backend/.claude/skills/kotlin-*`, 프론트엔드 `frontend/.claude/skills/frontend-react`, 공통 `.claude/skills/`.

각 스킬의 '적발 신호' 표에서 **Critical** 인 항목도 머지 차단 사유입니다.

## MUST — 위반 시 머지 차단

**자료형과 불변성**

- 공개 API 의 타입을 명시한다. 백엔드의 `Any`·`Map<String, Any>`·`!!`, 프론트의 `any`·습관적 `?`·`Record<string, unknown>`·사유 주석 없는 `unknown` 은 차단 사유다.

- 2개 이상의 연관 데이터를 넘길 때 raw map/tuple 대신 명시적 모델(data class, type) 을 쓴다.

- 도메인 모델과 DTO 는 불변이다. `var` 와 공개 세터를 만들지 않는다. 엔티티 상태는 `protected set` + 행위 메서드로만 바꾼다. 서비스가 엔티티 속성에 직접 대입하면 차단 사유다.

**경계와 방향**

- 레이어 방향은 상위 → 하위 단방향이다. 건너뛰기·역참조 금지. 백엔드는 controller → domain service → implement → repository, 프론트는 pages → hooks → services → api → lib.

- 엔티티는 `storage` 모듈 밖으로 나가지 않는다.

- 엔티티나 컬럼을 바꾸면 **같은 변경에 Flyway 마이그레이션이 포함된다.** 운영은 `ddl-auto: validate` 라 없으면 배포가 부팅에 실패한다. 이미 머지된 마이그레이션 파일을 수정·삭제하지 않는다.

- 도메인 경계를 넘는 직접 참조를 만들지 않는다. 다른 도메인의 구현 레이어·리포지토리를 직접 부르지 않고 그쪽 **서비스**를 통한다. 애그리게이트 경계 밖 연관관계 매핑, 한 트랜잭션에서 두 도메인의 상태 변경은 차단 사유다.

- enum 은 지정 위치에만 선언한다: 백엔드 `core:core-enum`, 프론트 `src/enums/`. 사용처 파일 안 인라인 선언은 차단 사유다.

**트랜잭션과 예외**

- 트랜잭션 경계는 도메인 서비스가 소유한다. 다단계 쓰기에 트랜잭션이 없으면 안 된다.

- 트랜잭션 안에서 외부 시스템을 호출하지 않는다.

- 예외를 뭉뚱그리지 않는다. `catch (e: Exception)` 은 전역 핸들러·배치 루프 같은 최상위 경계에서만 쓰고, 그 자리에서도 원인을 잃지 않고 로그를 남긴다.

  사유 주석 없는 포괄 catch, 원인을 버리는 예외 교체, 컨트롤러의 `try/catch` 는 차단 사유다.

**신뢰 경계와 보안**

- 신뢰 경계의 입력은 검증한다. `@Valid` 와 `@field:` 를 빠뜨리지 않는다. 미검증 입력을 쿼리·셸·파일 경로에 그대로 넣지 않는다.

- 소유자 스코프가 있는 데이터는 쿼리 조건으로 소유자를 건다.

- 비밀번호·토큰·키·개인정보를 코드·로그·응답·이슈 본문에 넣지 않는다.

- public API, DB 필드, 외부에서 쓰는 함수의 이름과 의미를 승인 없이 바꾸지 않는다.

**테스트**

- 새 동작(분기·정책·검증·상태 변경)에는 유닛 테스트가 같은 변경에 포함된다. 통과시키려고 테스트를 약화하거나 지우지 않는다.

- 유닛 테스트 메서드 하나는 기능 하나만 검증한다. 여러 시나리오를 한 메서드에 몰지 않는다.

**계약**

- `web` 노드가 만든 프론트 DTO 필드는 서버가 주는 이름 그대로여야 한다. `CONTRACT.md` 와 백엔드 응답 DTO 코드가 기준이고, 프론트에서 개명하지 않는다.

**변경 범위 — 요청한 것만, 최소한으로 고친다**

- 요청 범위 밖의 코드를 고치지 않는다. 손대는 파일과 줄은 요청을 만족시키는 데 필요한 만큼으로 제한하고, 지나가다 눈에 띈 코드는 그대로 둔다.

- 요청받지 않은 리팩터링·개선·이름 변경·구조 변경을 곁들이지 않는다. 고쳐야 할 것 같으면 직접 고치는 대신 PR 본문에 적어 사람이 판단하게 한다.

- 기존 코드를 고치지 않고 목적을 달성할 수 있으면 그쪽을 고른다. 기존 동작·시그니처를 바꿔야만 한다면 그 이유를 커밋 메시지에 남긴다.

- 리팩터링과 동작 변경을 같은 커밋에 섞지 않는다. 포맷팅만 바꾸는 변경도 로직 변경과 같은 diff 에 섞지 않는다.

- 위 넷을 어긴 diff 는 내용이 옳더라도 CHANGES_REQUESTED 사유다. 리뷰어는 "이 변경이 요청을 만족시키는 데 꼭 필요한가"를 파일·줄 단위로 묻는다.

## SHOULD — 참고 코멘트

- 특수 사례와 실패는 먼저 return/throw 하고, 정상 흐름을 마지막에 남긴다 (guard clause).

- 함수 이름은 동사로 시작한다. `Manager`·`Processor`·`Util` 류의 이름을 만들지 않는다.

- 한 번만 쓰이는 코드를 위해 추상화·base class·설정 옵션을 만들지 않는다.

- 주석은 규칙 예외와 특이사항에만 남긴다.

## 리뷰 범위 밖 — 지적 금지

- 포매팅, 줄 길이, import 순서 (ktlint·포매터가 처리).

- 스타일 취향과 네이밍 선호.

- 요청받지 않은 테스트 추가·리팩터링 제안.
